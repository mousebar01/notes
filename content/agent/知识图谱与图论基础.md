# 知识图谱与图论基础

这篇笔记只保留多模态 RAG 真正需要的知识图谱知识：怎样描述文档中的对象和关系，怎样设计 Schema、构建和存储图谱，以及怎样把图检索与向量检索组合起来。图论部分也只解释会直接影响检索实现的概念。

## 核心模型

知识图谱把知识表示为节点和边。最小表达是三元组：

```text
(head, relation, tail)
(头实体, 关系, 尾实体)
```

例如：

```text
(TextChunk_13, references, Image_2)
(Image_2, located_in, Page_4)
(Table_1, supports, Claim_A)
```

工程上通常使用属性图：节点和边除了类型，还能携带属性。

### 节点、边与属性

- **节点 / 实体**：一个可独立标识的对象。
- **边 / 关系**：两个节点之间有方向的语义连接。
- **属性**：节点或边自身的数据，不需要额外建成节点。

多模态文档中的节点可以分为三组：

| 分组 | 常见类型 | 作用 |
| --- | --- | --- |
| 文档结构 | `Document`、`Page`、`Section` | 保留来源和层级 |
| 内容单元 | `TextChunk`、`Image`、`Table`、`Formula`、`Caption` | 连接不同模态的证据 |
| 语义对象 | `Entity`、`Concept`、`Claim`、`Metric` | 支持跨文档关系和推理 |

节点属性适合保存：

```json
{
  "id": "Image_2",
  "type": "Image",
  "document_id": "Document_1",
  "page": 4,
  "bbox": [80, 300, 500, 620],
  "caption": "系统整体架构图",
  "source_uri": "s3://docs/paper.pdf"
}
```

边也应保留证据和可信度：

```json
{
  "from": "TextChunk_13",
  "relation": "explains",
  "to": "Image_2",
  "confidence": 0.87,
  "method": "llm_extraction",
  "evidence": "如图 2 所示",
  "source_uri": "s3://docs/paper.pdf#page=4"
}
```

把 `source_uri`、`method`、`evidence` 和 `confidence` 记录在边上很重要。图谱中的关系可能来自版面规则、人工标注或模型推断，它们的可信程度并不相同。

## Schema 与 Ontology

Schema 规定图中允许出现什么：

- 有哪些节点类型；
- 有哪些关系类型及方向；
- 哪些类型之间可以建立某种关系；
- 每种节点和边需要哪些属性；
- 唯一标识、必填字段和基数约束是什么。

一个面向多模态文档的最小 Schema 可以是：

```text
节点：
Document, Page, Section
TextChunk, Image, Table, Formula, Caption
Entity, Claim, Metric

关系：
Document -contains-> Page
Page -contains-> TextChunk | Image | Table | Formula
Section -contains-> TextChunk | Image | Table | Formula
TextChunk | Image | Table | Formula -located_in-> Page
Image | Table -has_caption-> Caption
TextChunk -references | explains-> Image | Table | Formula
Table | Image -supports-> Claim
TextChunk | Image | Table -mentions-> Entity
Formula -defines-> Metric
```

Schema 的价值不是让命名更整齐，而是让构建、查询和评估使用同一套语义。如果同一种关系同时叫 `references`、`refers_to`、`mentions_figure` 和 `cites`，后续查询会漏结果，也很难比较抽取质量。

设计时要先固定：

1. 关系方向，例如 `TextChunk -references-> Image`。
2. 是否需要反向关系，还是查询时反向遍历。
3. 结构关系与语义关系的边界，例如“同页”是可验证结构，“解释”是语义判断。
4. 属性和节点的边界：页码通常是属性，页面本身需要参与路径时才建为节点。
5. 每条推断关系能否回到原始证据。

### Ontology 什么时候需要

Ontology 是更严格的概念模型，还会表达类别层级、逻辑约束和领域规则，例如：

```text
Company subClassOf Organization
Drug treats Disease
Drug contraindicated_for Population
```

普通文档 RAG 通常先有稳定 Schema 就够了。医疗、金融、法律等领域需要统一概念层级、校验约束或规则推理时，再引入更完整的 Ontology。过早建复杂本体会增加维护成本，却不一定提升检索质量。

## 构建流程

可靠的图谱通常同时使用确定性规则和模型抽取。

### 1. 解析文档结构

先把原始文件拆成稳定单元：

```text
Document
→ Page
→ Section
→ TextChunk / Image / Table / Formula / Caption
```

每个单元都要有稳定 ID、来源文件、页码或位置。图片和表格最好保留边界框及对象存储地址，便于回答时取回原件。

### 2. 建立确定性结构边

从解析结果直接生成高可信关系：

```text
Document contains Page
Page contains Image
Section contains TextChunk
Image has_caption Caption
Image located_in Page
```

同页、同章节、标题归属和版面邻近也可以由规则生成，但不要把“靠得近”直接当成“解释”或“支持”。

### 3. 抽取语义实体和关系

NLP、LLM 或 VLM 可以识别：

```text
(RAG, consists_of, Retriever)
(TextChunk_13, explains, Image_2)
(Table_1, supports, Claim_A)
(Image_2, contains_entity, Reranker)
```

模型抽取更灵活，也更容易产生关系方向错误、同义实体重复或无证据推断。输出应受 Schema 约束，并保留抽取方法、原始证据和置信度。

| 来源 | 适合建立的边 | 特点 |
| --- | --- | --- |
| 解析规则 | `contains`、`located_in`、`has_caption` | 稳定、可复算 |
| 文本模型 | `mentions`、`defines`、`supports` | 需要实体消歧和证据 |
| 视觉模型 | 图中对象、流程和视觉关系 | 需要回看图片验证 |
| 人工标注 | 高价值领域关系 | 成本高，但可作为评估基准 |

### 4. 实体规范化与去重

“RAG”“Retrieval-Augmented Generation”和“检索增强生成”可能是同一概念。入图前需要：

- 规范名称和别名；
- 使用文档内 ID 或领域唯一 ID；
- 结合类型、上下文和来源做实体消歧；
- 合并重复节点，同时保留各自证据；
- 不确定时保持分离，不要强行合并。

如果跳过这一步，图会看似丰富，实际被大量重复节点割裂。

### 5. 校验与增量更新

至少检查：

- 节点 ID 是否唯一，边的两端是否存在；
- 关系是否符合 Schema 的类型和方向；
- 模型边是否有证据，置信度是否达到阈值；
- 删除或更新文档时，旧节点和边能否追踪；
- 同一数据重新处理时，是否会生成重复记录。

图谱应当可以从原始文档和抽取版本重建。它是派生索引，不应成为唯一事实来源。

## 存储方式

选择存储取决于图规模和查询复杂度。

| 方式 | 适用阶段 | 优点 | 局限 |
| --- | --- | --- | --- |
| CSV / JSON 三元组 | 实验验证 | 直观、容易检查 | 并发更新和复杂查询弱 |
| SQLite / PostgreSQL 节点边表 | PoC 到中型系统 | 运维简单、事务成熟 | 多跳查询写法较繁琐 |
| Neo4j / NebulaGraph 等图数据库 | 关系查询成为核心后 | 路径和子图查询自然 | 增加独立基础设施 |
| 向量数据库 | 语义召回 | 擅长相似内容 | 不表达精确关系 |
| 对象存储 | PDF、图片、表格原件 | 保存大对象 | 不负责检索关系 |

多模态 RAG 常见的组合是：

```text
向量库    → 文本、图片摘要、实体描述的 embedding
图或关系表 → nodes、edges、provenance
对象存储  → PDF、原图、表格文件
```

各存储之间用稳定的 `document_id`、`node_id` 和版本号关联。早期不必为了“用了知识图谱”就引入图数据库；节点表、边表已经能验证 Schema 和检索价值。

## 图检索与向量检索

两者是互补关系：

| 能力 | 图检索 | 向量检索 |
| --- | --- | --- |
| 擅长 | 显式关系、类型过滤、多跳路径 | 语义相似、模糊表达 |
| 依赖 | 已经正确建出的节点和边 | 高质量 embedding 与切块 |
| 常见失败 | 缺边导致漏召回，扩展过宽带来噪声 | 相似但无事实关系，难表达路径 |
| 在 RAG 中 | 扩展和组织证据 | 找到初始候选 |

一个实用的混合检索流程是：

```text
用户问题
→ 识别实体、意图和关系约束
→ 向量 / 关键词召回初始节点
→ 映射到图中实体或内容单元
→ 按允许的关系扩展 1–2 跳
→ 得到相关证据子图
→ 合并、去重、打分和 rerank
→ 取回文本、图片、表格原件
→ 生成带来源的回答
```

初始召回解决“从哪里进入图”，关系扩展解决“还应带上哪些关联证据”。如果问题已经包含明确实体和关系，也可以直接从图查询开始。

### 查询示例

查找引用标题含“架构”的图片的文本块：

```cypher
MATCH (t:TextChunk)-[:REFERENCES]->(i:Image)
WHERE i.caption CONTAINS "架构"
RETURN t, i
```

查找支持某个结论的图表及其页码：

```cypher
MATCH (e)-[:SUPPORTS]->(c:Claim {id: "Claim_A"})
MATCH (e)-[:LOCATED_IN]->(p:Page)
RETURN e, p
```

查询结果不应只返回节点名称，还要返回路径和来源证据。否则生成模型无法判断某张图为什么与问题相关，也难以给出可核查引用。

## 多跳检索所需的图概念

| 概念 | 在 RAG 中的含义 |
| --- | --- |
| 有向边 | `A → B` 不等于 `B → A`；关系方向决定查询语义 |
| 加权边 | 用置信度、相似度或规则权重表达关系强弱 |
| 邻居 | 与当前节点直接相连的 1-hop 节点 |
| 路径 | 从初始实体到证据节点经过的一组关系 |
| 跳数 | 路径包含的边数；越多召回越广，噪声通常也越大 |
| 子图 | 针对当前问题抽取的一小组节点、边和证据 |
| 度 | 节点连接数量，可用于发现枢纽，也可能暴露错误的过度连接 |
| BFS | 按 1-hop、2-hop 逐层扩展，适合受限邻域检索 |
| 中心性 | 可辅助判断被多处引用的节点，但不能替代问题相关性 |

多跳的例子：

```text
Section_2 -contains-> Table_1
Table_1 -supports-> Claim_A
```

问题“支持结论 A 的表格在哪一节”需要从 `Claim_A` 反向找到 `Table_1`，再反向找到 `Section_2`。图的价值在于显式保存这条两跳证据路径，而不是让模型从几个相似文本中猜测。

### 控制图扩展噪声

图扩展不是跳数越多越好。常用限制包括：

- 最大跳数通常先从 1–2 跳开始；
- 只允许与当前问题有关的关系类型和方向；
- 设置边置信度、时间和来源过滤；
- 每层限制候选数量，并对高出度节点降权；
- 记录已访问节点，避免在环中重复遍历；
- 优先保留能回到原始证据的路径；
- 图分数与向量相关性一起进入 rerank。

图太稀疏时，多模态证据互相连不起来；图太稠密时，任何内容都能经几跳关联，检索失去区分度。边的质量通常比边的数量更重要。

## 最小多模态示例

假设 PDF 第 4 页有一段正文和一张架构图：

```text
正文：如图 2 所示，系统由 Retriever、Reranker 和 Generator 组成。
图片：图 2，系统架构图。
```

最小图可以是：

```text
(Document_1, contains, Page_4)
(Page_4, contains, TextChunk_13)
(Page_4, contains, Image_2)
(Image_2, located_in, Page_4)
(Image_2, has_caption, Caption_2)
(TextChunk_13, references, Image_2)
(TextChunk_13, mentions, Retriever)
(TextChunk_13, mentions, Reranker)
(TextChunk_13, mentions, Generator)
(Image_2, contains_entity, Retriever)
(Image_2, contains_entity, Reranker)
(Image_2, contains_entity, Generator)
(Retriever, flows_to, Reranker)
(Reranker, flows_to, Generator)
```

用户问“Reranker 后面接什么”时，可以从实体 `Reranker` 沿 `flows_to` 找到 `Generator`，再取回 `Image_2` 和 `TextChunk_13` 作为共同证据。

用户问“这段文字引用了哪张图”时，可以直接查询：

```text
TextChunk_13 -references-> Image_2
Image_2 -located_in-> Page_4
```

同一份图同时支持精确关系查询和跨模态证据组合，这才是它相对单纯向量召回的增量价值。

## 实施顺序与边界

一个稳妥的落地顺序是：

1. 先定义最小 Schema 和稳定 ID。
2. 用解析规则建立文档、页面、内容单元和 caption 的结构边。
3. 用节点表、边表完成一组真实问题的检索闭环。
4. 加入向量召回，验证图扩展是否提升跨模态证据召回。
5. 再引入模型抽取的语义边，并用人工样本评估准确率。
6. 多跳查询和图更新成为瓶颈后，再评估图数据库。
7. 只有出现明确需求时，才增加复杂 Ontology 或图嵌入。

评估不能只看图中有多少节点和边，更应回答：

- 问题需要的文本、图片和表格是否一起被召回；
- 图扩展相对纯向量检索增加了多少有效证据和噪声；
- 每条回答能否回溯到路径和原始文档；
- 实体去重、关系方向和模型抽取错误占比如何；
- 文档更新后，图和向量索引是否保持一致。

知识图谱不是自动产生事实的推理引擎。没有建出的边不代表关系不存在，模型抽取出的边也不天然为真。它最适合承担的是：把多模态证据之间已经识别出的结构和语义关系显式保存，让检索可以沿着这些关系组成一份可解释、可追溯的证据子图。
