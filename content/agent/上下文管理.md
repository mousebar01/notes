# Agent 上下文管理

上下文管理不是把所有信息拼进 prompt，而是在有限窗口中决定哪些信息保留原文、按需检索、压缩替代或放进 API 原生字段。

## 单轮主线

```text
用户输入
  -> 输入预处理与风险检查
  -> 构建 runtime context
  -> 组装 messages 与 tools
  -> 模型 / 工具循环
  -> 输出与产物
  -> 持久化历史和长期信息
```

工具循环内部是：

```text
模型生成 tool call
  -> policy / hook / 参数检查
  -> 执行工具
  -> tool result 回填
  -> 模型继续或结束
```

## 信息应该放在哪里

| 信息 | 推荐位置 |
| --- | --- |
| 身份、稳定规则 | system prompt |
| 当前用户请求 | user message |
| 历史对话 | messages history |
| 本轮工具结果 | tool message |
| 按需召回的记忆 | 临时 runtime context 或本轮消息副本 |
| 工具参数定义 | API 原生 `tools` schema |
| 模型、温度、tool choice | payload 控制字段 |

工具使用原则可以写进 system prompt，但完整 schema 不应同时再复制成大段文本。关于 `messages`、`tools` 和控制字段的边界，统一参考 [DeepSeek HTTP payload 结构](../llm/DeepSeek%20HTTP%20payload%20结构.md)。

API role 是消息级身份边界；XML 或 Markdown 标签只是 `content` 内部的语义分块，不能替代 role 和 tool schema。

## 稳定上下文与临时上下文

为了保持行为和 prompt cache 前缀稳定，可以按变化频率分层：

```text
stable      身份、规则、工具原则
session     项目说明、用户偏好、会话配置
per-turn    当前请求、检索结果、工具结果
ephemeral   调试信息、一次性提示和临时兼容字段
```

本轮模型需要知道的信息，不一定都值得写进永久会话历史。检索结果和临时插件上下文适合注入本轮请求副本，避免长期污染 session。

## 记忆与压缩不是一回事

- **长期记忆**回答哪些事实值得保存、未来如何召回。
- **上下文压缩**回答当前会话太长时如何继续工作。
- **历史搜索**用于按需找回过去的具体细节。

把所有历史都写进 memory，会增加每轮成本并把临时事实升级成长期事实；直接删除旧消息又会丢失目标、决策和进度。

## Token 预算

上下文预算至少要扣除预期输出和安全余量：

```text
usable_input = context_window - reserved_output - safety_margin
```

构建过程中可以用字符数或经验比例快速预警；正式调用前尽量使用接近目标模型的 tokenizer。代码、JSON、工具 schema 和混合语言的 token 密度差异较大，粗略估算必须留余量。

模型最终消费的是 provider 渲染后的 token 序列，而不是原始 JSON 字节数。无法获得服务端精确渲染格式时，应把 schema、角色标记等额外开销计入安全余量。

## 分层降级

接近窗口上限时，可以逐级处理：

1. 截断或替换过大的旧工具结果。
2. 删除已经失效的临时上下文和重复 schema 文本。
3. 用结构化摘要替代较旧的完整回合。
4. 保留最近原始消息和当前未完成动作链。
5. 仍然超限时，再缩小检索结果或拆分任务。

完整 compaction 需要保护 tool call 与 tool result 配对，并保存目标、约束、进度、决定、文件和下一步。具体算法与 Branch Summary 见 [Pi Agent 学习笔记](./Pi%20Agent%20学习笔记.md)。

## 检查清单

- 同一信息是否同时出现在 system、history 和 tool schema？
- 本轮检索结果是否被错误地永久写入历史？
- token 预算是否为输出和估算误差留出空间？
- 压缩是否保留当前目标、未完成动作和工具因果链？
- 过期权限、旧工具结果和临时调试信息是否仍在上下文里？
- 是否能从持久 session 找回完整事实，而不是只剩摘要？

一句话总结：把稳定规则、会话状态、本轮证据和工具定义放到各自正确的位置，再用预算与分层压缩控制窗口压力。
