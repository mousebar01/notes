# 零信任与 Agent 时代安全

## 背景

零信任（Zero Trust）是网络安全行业的正式术语，也是 Tailscale 等现代组网工具的设计哲学。在 Agent（AI 编程代理、自主智能体）时代，零信任的含义和落点发生了变化：信任主体从"人"变成了"自主行动的 AI"。这篇梳理概念本身，以及 agent 时代需要零信任的环节。

## 零信任是什么

- 2010 年 Forrester 分析师 John Kindervag 提出"Zero Trust"框架
- **2020 年 NIST SP 800-207**《Zero Trust Architecture》正式标准化

核心一句话：**永不信任，始终验证**（Never trust, always verify）。

```
传统"边界防御"（城堡护城河）:
  内网 = 可信 ✅   外网 = 不可信 ❌
  进了内网 = 默认信任（内鬼最难防；边界一破，内网裸奔）

零信任:
  没有"内网可信"这回事
  每一次访问，不管来自哪里，都要:
    ① 验证身份（你是谁/它是哪台设备）
    ② 检查授权（你被允许访问这个吗）
    ③ 加密传输（沿途不裸奔）
```

### 三原则（NIST 口径）

| 原则 | 含义 |
|------|------|
| 身份是边界 | 不信任位置，信任身份 |
| 最小权限 | 只给必要访问权 |
| 持续验证 | 每次请求都验，不搞一次放行 |

## 去中心化与信任模型

"去中心化"要分清去的是哪一层（以 Tailscale 和加密货币为例）：

| | 去中心化位置 | 说明 |
|---|---|---|
| Tailscale | **传输**去中心化 | 数据面设备直连，但控制面（身份/策略/密钥）仍是中心 |
| 加密货币 | **信任**去中心化 | 无中心记账，靠共识算法；网络本身公开无需许可 |

类比："Tailscale 解决的是'路'的问题，加密货币解决的是'账'的问题"。点对点**传输**早已实现（加密隧道传什么都行），但点对点**交易**（无中间人转账）还需要账本+共识，tailnet 本身不提供（闪电网络是"P2P 通道 + 链上结算"的典型）。

完全去中心化很少见，都是务实妥协：比特币算力集中在矿池，Tailscale 有 DERP 兜底 + 中心控制面。

## Agent 时代的变化：为什么更需要零信任

传统零信任防的是"人"：人有判断力、有责任感、行动慢。Agent 恰好反着来：

| 特性 | 风险 |
|------|------|
| 非人类主体 | 无法追究责任、没有"常识" |
| 自主行动链 | 一个错误决定可以连锁执行几十个工具调用 |
| 机器速度 | 出问题以毫秒计，人来不及拦 |
| 可被注入 | **提示注入**（网页/文档里的恶意指令劫持 agent）是全新攻击面 |
| 越权放大 | 一个 agent 拿到的能力可能被另一个 agent/工具间接利用 |

所以 agent 时代的零信任要在**"工具调用"这个粒度**上做验证。

## Agent 时代需要零信任的环节

| 环节 | 风险 | 零信任做法 | 实例 |
|------|------|-----------|------|
| 工具权限 | agent 拿到 bash 就能删库 | 工具白名单 + 每次调用校验 | pi 的 `--tools`、subagent 工具白名单 |
| 文件/仓库访问 | 读不该读的、改不该改的 | 按项目/路径授权，进新项目要验证 | pi 的 project trust（AGENTS.md 信任流程） |
| 凭据管理 | agent 要用 API key | 最小权限 key、短时效、按任务签发 | Tailscale API key 只给 acl 读写 + 短有效期 |
| 网络出口 | agent 偷偷外联/数据外泄 | 出口白名单、按目标授权 | tailnet grants 控制谁能访问 |
| 多 agent 编排 | 子 agent 越权、权限放大 | 每个子 agent 独立身份 + 独立白名单 + 深度限制 | pi-subagents：每个角色独立 system prompt/工具/模型 |
| 执行环境 | agent 代码裸跑 | 沙箱/容器隔离 | 容器化 agent runner |
| 人类审批门 | 不可逆操作（部署/付款/删数据） | 高风险动作必须人工闸门 | watchdog 审查、approval 机制 |
| 审计 | 出了事查不了 | 全链路日志、非抵赖 | 会话导出、tool 调用日志 |

## Agent 专属威胁：提示注入

传统攻击是"攻破系统 → 偷数据"；agent 时代多了"往网页/README 里埋指令 → agent 读到时被劫持 → agent 自己动手"。对应措施：

- **上下文隔离**：外部内容（网页、文档）和可信指令（系统提示）分离
- **工具能力最小化**：读外部内容用只读沙箱，不给写权限
- **关键操作人工确认**：不可逆动作触发审批

## 业界正在形成的规范

- **OWASP LLM Top 10**：提示注入、敏感信息泄露、供应链漏洞在列
- **Agent 身份**：给 agent 发独立身份/凭据，不借用人的（tailnet 的 tag 身份就是"机器身份 ≠ 用户身份"的思路）
- **MCP 安全**：每连一个 MCP 服务器都是新的攻击面
- **能力安全（capability-based）**：不说"agent 能访问数据库"，而说"agent 在 X 任务下能对 Y 表执行 SELECT"——正是 ACL/grants 的粒度思想

## 结论 / 经验

- 传统零信任是"对人验证"，agent 时代的零信任是"对每一次工具调用验证"
- 一个值得先记着的判断：**不要把"能跑"误当成"允许跑"**（与 security 专题 README 的判断一致）
- 对 Agent 系统，安全测试可以直接假设模型已被诱导成功，然后检查工具调度层和执行环境是否仍能拦住越权动作
