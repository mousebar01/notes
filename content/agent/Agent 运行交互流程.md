# Agent 运行交互流程

这篇从用户和前端视角记录一次 Agent Run 的交互闭环，重点是输入、执行过程、来源展示和继续追问，不重复平台内部的扩展架构。

## 完整闭环

```text
选择上下文
  -> 输入需求
  -> 创建 Agent Run
  -> 流式执行模型与工具
  -> 返回回答、来源和产物
  -> 反馈、重试或继续追问
```

## 1. 选择上下文

一次运行通常受以下信息约束：

- 当前 Agent、模型和会话线程
- 可访问的知识库、工具、Skill 与 MCP
- 用户权限、租户和工作空间
- 附件、线程文件和已有产物

前端不一定把所有配置暴露给用户，但后端必须把它们固化为可审计的运行输入。

## 2. 创建 Run

用户提交消息后，系统创建或复用 thread，并为本次执行记录 run。run 至少需要关联输入、Agent 配置、状态、开始结束时间和错误；长任务还需要取消、重试与恢复语义。

具体能力如何挂载见 [Agent 平台集成设计](./Agent%20平台集成设计.md)。

## 3. Agent 决定下一步

Agent 可以直接回答，也可以检索知识库、调用工具、委派子 Agent 或生成文件。每次工具结果都会回到运行上下文，模型再决定继续执行还是结束。

```text
模型输出 tool call
  -> 权限和参数校验
  -> 执行工具
  -> 记录 tool result
  -> 模型继续推理
```

## 4. 流式展示

前端需要区分最终内容和过程事件：

| 类型 | 示例 |
| --- | --- |
| 最终内容 | 回答、报告、文件和结构化结果 |
| 过程事件 | 检索、工具调用、子任务状态、重试和错误 |

过程展示应帮助用户判断进度和风险，不应把原始内部 trace 全部倾倒到聊天流。

## 5. 来源与产物

来源适合按类型和文件组织，并保留 chunk、页码、时间戳、URL 或相似度等定位信息。用户应能从结论回到证据，但来源详情不必打断正文阅读。

生成文件、图片或其他产物则需要关联 run、保存位置、生成状态和后续操作，不能只作为一条临时消息存在。

## 6. 后续操作

回答结束后，用户可能：

- 复制、评价或重新生成。
- 展开来源和工具详情。
- 下载或继续处理产物。
- 在同一 thread 中追问。
- 从失败点重试或取消长任务。

继续追问时应复用必要的 thread state，但不能默认继承已经失效的权限、临时工具结果或过期外部数据。

一句话总结：用户负责表达目标，Agent 负责执行决策，界面负责把过程、结果、证据和产物分层呈现。
