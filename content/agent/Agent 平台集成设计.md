# Agent 平台集成设计

这篇从架构视角记录“对话入口 + Agent 运行核心 + 可挂载能力”的平台边界。用户通过自然语言表达目标，Agent 负责选择和组合能力，具体执行由知识库、工具、Skill、MCP、子 Agent 或沙箱完成。

## 核心结构

```text
对话入口
  -> Agent runtime
      -> 模型
      -> 知识库 / 知识图谱
      -> Tool / Skill
      -> MCP 外部能力
      -> 子 Agent
      -> 沙箱
  -> 回答、来源和产物
```

Agent 不是简单的模型调用封装。它承担的是运行时编排：维护上下文和状态，根据权限与可用能力决定下一步，并将工具结果重新送回模型或转换为最终产物。

## 能力边界

| 能力 | 主要职责 | 不应承担的职责 |
| --- | --- | --- |
| 知识库 | 文档解析、索引和检索 | 任意业务操作 |
| 知识图谱 | 显式实体关系与关系查询 | 替代全部语义检索 |
| Tool | 提供一个边界明确的动作 | 隐藏长流程和持久状态 |
| Skill | 封装任务方法、提示和工具组合 | 复制平台核心 runtime |
| MCP | 以协议接入外部系统能力 | 成为所有内部能力的唯一形式 |
| 子 Agent | 委派独立认知任务 | 承载所有后台数据处理 |
| 沙箱 | 隔离高风险执行 | 代替权限判断和审批 |

新增能力时，优先选择最窄的接入形式，而不是把逻辑继续堆进主聊天流程。

## MCP 的位置

MCP 适合连接数据库、代码仓库、企业服务和第三方 API。它解决外部能力如何以统一协议暴露，不替代平台内部的 Tool、Skill、知识库或任务系统。

```text
外部系统 -> MCP adapter -> Agent 可见工具
内部能力 -> Tool / Skill / service -> Agent runtime
```

## 企业场景需要补上的边界

- 用户、租户和角色能访问哪些 Agent、知识库和工具。
- 工具调用是否需要审批、审计和沙箱。
- 来源和产物如何关联到具体 run。
- 长任务如何持久化、重试、取消和恢复。
- 模型、凭证和外部系统配置如何隔离。

界面交互与流式事件详见 [Agent 运行交互流程](./Agent%20运行交互流程.md)。

一句话总结：用对话统一用户入口，用 Agent 承接运行决策，用边界清晰的扩展机制连接知识、工具和外部系统。
