# 后台任务租约与恢复

> 来源状态：从 Hermes worker 笔记提炼的**个人总结**，未针对某个任务框架做**源码验证**。文中的状态名和参数是通用示例，不代表某个项目已经实现；落地细节均需结合目标系统**待确认**。

后台任务最难的不是“启动 worker”，而是 worker 中断、假死或重复执行后，任务仍能回到一个可判断、可恢复的状态。

## 基本模型

~~~text
producer -> durable queue / task table -> worker
                    ^                  |
                    +---- status ------+
~~~

| 概念 | 作用 | 不能证明什么 |
| --- | --- | --- |
| Heartbeat | worker 定期更新“我还能与任务系统通信” | 任务一定有业务进展 |
| PID liveness | 本机进程是否仍存在 | 进程没有假死、阻塞或死循环 |
| TTL | 某个状态或占用权的有效期 | 超时一定意味着 worker 已死亡 |
| Lease | 带到期时间、可续约的临时执行权 | 永久所有权 |
| Claim token | 标识当前 lease owner | 外部副作用只执行一次 |
| Run id | 区分同一 Task 的不同尝试 | 任务本身天然幂等 |

Heartbeat 是信号，TTL 是判断窗口，Lease 是由二者维护的执行权。

## 生命周期

一个最小状态流是：

~~~text
ready
  -> atomic claim(token, run_id, expires_at)
running
  -> renew lease / heartbeat
  -> complete
  -> block
  -> lease expires -> reclaim -> ready
failed repeatedly
  -> dead letter / manual review
~~~

关键点是 claim 必须原子完成。先读取再普通写入，会让多个 worker 同时认为自己领取成功。

## 存活信号

| PID | Heartbeat | 可能情况 | 建议 |
| --- | --- | --- | --- |
| 存在 | 正常 | 大概率可运行 | 继续观察 |
| 存在 | 超时 | 假死、长阻塞、状态层不可达 | 等宽限期后回收或人工检查 |
| 不存在 | 停止 | 进程退出或崩溃 | 结束 Run 并释放 lease |
| 不可检查 | 正常 | 远程 worker、容器或跨主机场景 | 以 lease / heartbeat 为主 |

PID 只适用于能可靠观察本机进程的场景。远程执行不能把“查不到 PID”直接当作崩溃。

Heartbeat 也可能误报：数据库短暂不可用、网络抖动、GC、CPU 饥饿或长时间阻塞调用，都可能让正常 worker 晚报。超时策略需要容忍抖动。

## 参数关系

通常应满足：

~~~text
heartbeat interval < heartbeat timeout < task max runtime
~~~

例如每 30 秒心跳、2 到 5 分钟后判定失联，只是起始假设，不是通用答案。参数应根据以下因素确定：

- 正常任务最长多久不返回控制权。
- 状态存储和网络的抖动范围。
- 重复执行的成本。
- 故障后多久必须恢复。

高副作用任务宁可慢一点回收，也不要激进地产生双执行；低风险、可幂等任务可以更快重试。

## 回收时的正确性

Lease 过期后，旧 worker 可能并没有真正停止。系统应按“至少一次执行”而非“恰好一次执行”设计。

### 1. Fencing

每次 claim 生成单调递增的版本或唯一 token。提交结果时必须带上当前 token / run id：

~~~sql
UPDATE tasks
SET status = 'done'
WHERE id = ?
  AND status = 'running'
  AND claim_token = ?
  AND run_id = ?;
~~~

更新行数为 0，说明 worker 已过期，不能覆盖新 Run。

### 2. 幂等

Fencing 只能保护任务表，不能撤销旧 worker 已经产生的外部副作用。发送邮件、扣款、创建订单等操作需要业务幂等键或去重表。

~~~text
task id / operation id
  -> idempotency key
  -> external system rejects duplicate
~~~

### 3. 可中断执行

回收旧 lease 后，尽量向旧 worker 发送取消信号；但系统不能依赖取消一定成功。最终正确性仍要靠 fencing 与幂等。

## 重试与 Dead Letter

先区分失败类型：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 瞬时失败 | 网络抖动、限流、短暂不可用 | 指数退避并加随机抖动 |
| 配置失败 | 缺密钥、命令不存在、权限不足 | 立即阻塞，等待人工修复 |
| 业务失败 | 输入非法、前置条件不成立 | 记录原因，不盲目重试 |
| 超时或崩溃 | worker 消失、lease 过期 | 回收后创建新 Run |

每个 Task 应有 retry count、max retries 和 last error。超过上限后进入 Dead Letter 或人工处理区，避免坏任务无限消耗资源。

Dead Letter 不是垃圾桶。它至少要保留：

- 最后错误与失败分类。
- 每次 Run 的时间、worker 和退出原因。
- 输入摘要与幂等键。
- 人工重放或终止入口。

## 观测与审计

`last_heartbeat_at` 适合回答“现在是否健康”，Event / Run history 适合回答“之前发生了什么”。

每次 heartbeat 都永久写 Event 可能制造大量日志，可以选择：

- 只更新最新心跳时间。
- 定期采样 heartbeat event。
- 只在 healthy -> stale 等状态变化时记录事件。

至少应监控：

- running Task 中 lease 即将或已经过期的数量。
- ready 很久却无人领取的 stranded Task。
- 每类失败的重试次数和 Dead Letter 增长。
- 单个 worker / assignee 的心跳延迟和成功率。
- 回收后旧 Run 继续写入而被 fencing 拒绝的次数。

## 设计检查清单

- Claim 是否通过原子条件更新完成？
- Lease 是否有 owner、到期时间和续约机制？
- 新 Run 能否阻止旧 worker 提交？
- 外部副作用是否有幂等键？
- 超时是否为正常抖动留出宽限？
- 重试是否区分瞬时、配置和业务失败？
- 是否有最大重试次数与人工接管入口？
- 当前状态与历史审计是否分开保存？
- 远程 worker 是否避免依赖本机 PID？
- 恢复流程是否经过“双 worker 并存”测试？

一句话：Heartbeat 负责报告，TTL 负责过期判断，Lease 负责临时所有权，fencing 和幂等负责重复执行下的正确性，Dead Letter 负责停止无意义的无限重试。
