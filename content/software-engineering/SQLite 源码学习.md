# SQLite 源码学习

这篇笔记只抓 SQLite 最值得反复回看的主线：一条 SQL 如何被编译为指令，再由执行器落到存储层。目标不是记住所有源码文件，而是理解每一层在替谁承担变化。

> 整理说明：早期学习过程和类比例子保存在 `archive/topics/software-engineering/SQLite 源码学习-原稿.md`。这里保留经过收敛的理解，并标出仍需结合具体版本验证的细节。

## 为什么从这条链路开始

第一次看 SQLite，很容易在 Parser、VDBE、BTree、Pager 等名词之间来回跳。更有效的方式是先追踪一个简单查询，只问四个问题：

1. SQL 在哪里被理解？
2. 查询意图在哪里变成可执行步骤？
3. 谁维护执行时的寄存器、游标和控制流？
4. 谁真正读取记录和页面？

这些问题最终落在同一条链路上：

```text
SQL 字符串
  -> Tokenizer / Parser：识别 token、语法和语义结构
  -> Code Generator：选择操作并生成 VDBE program
  -> VDBE：按 opcode 驱动寄存器和游标
  -> BTree：按表或索引的树结构查找、读取和修改记录
  -> Pager / VFS：管理页面、事务、缓存、锁与操作系统 I/O
```

先记住这张图就够了。后面的文件和函数都只是把图中的某一段展开。

## 各层分别负责什么

| 层 | 输入 | 输出或职责 | 不应知道的事 |
| --- | --- | --- | --- |
| Tokenizer / Parser | SQL 文本 | token、语法动作和查询结构 | 页面如何落盘 |
| Code Generator | 已解析的语句和查询规划结果 | 一组 VDBE 指令 | 操作系统怎样读文件 |
| VDBE | opcode program | 执行状态、寄存器、游标和结果行 | SQL 原文怎样书写 |
| BTree | 表或索引游标操作 | 有序查找、记录访问和修改 | `SELECT`、`UPDATE` 等语法 |
| Pager / VFS | 页面请求 | 缓存、事务、锁、日志和 I/O | 上层为何读取这条记录 |

这里的关键不是“层越多越好”，而是每一层都有自己的信息边界。Parser 面对语言变化，VDBE 面对执行语义，BTree 面对数据组织，Pager 面对页面与持久化。

## VDBE 的位置

VDBE 全称是 **Virtual Database Engine**。它执行 SQLite 自己定义的 opcode，是 SQL 语义与存储操作之间的稳定中间层。

可以把它类比为字节码解释器，但不用把它等同于通用 CPU 或 JVM。VDBE 的指令、寄存器和游标都围绕数据库操作设计，例如：

- 打开表或索引游标；
- 定位某个 rowid 或索引键；
- 从记录中取列；
- 比较值并跳转；
- 生成结果行；
- 插入、删除或更新记录。

如果没有这个中间层，每种 SQL 语句都可能直接调用 BTree。这样语法、执行控制和存储细节会缠在一起。VDBE 把关系收敛为：前端负责生成统一指令，后端负责执行这些指令并操作存储。

## 一个 opcode 程序示例

假设有表：

```sql
CREATE TABLE user (
  id INTEGER PRIMARY KEY,
  name TEXT
);

SELECT name FROM user WHERE id = 3;
```

使用 `EXPLAIN` 查看时，可能得到类似下面的程序。地址、参数和具体指令会随 SQLite 版本、表结构和优化结果变化，这里只保留主干：

```text
addr  opcode       p1  p2  p3  p4
0     Init          0   8   0
1     OpenRead      0   2   0   2
2     Integer       3   1   0
3     SeekRowid     0   7   1
4     Column        0   1   2
5     ResultRow     2   1   0
6     Halt          0   0   0
```

读这段程序时，不要先背 `p1` 到 `p4`，而要看状态怎样流动：

- `OpenRead` 创建读游标；
- `Integer` 把查询常量放进寄存器；
- `SeekRowid` 用寄存器里的值定位记录；
- `Column` 从当前记录解出 `name`；
- `ResultRow` 把寄存器中的值交给调用方；
- 找不到记录时跳到结束位置。

这个例子也说明：VDBE program 不是 SQL 的逐词翻译。Parser、查询规划和代码生成已经决定了“按 rowid 定位”这一执行策略。

## 从哪里读源码

SQLite 官方提供 amalgamation（合并后的 `sqlite3.c`）和分文件源码。学习模块边界时，分文件版本更容易定位；确认真实发布代码时，再回到 amalgamation 对照。

| 文件 | 阅读目的 |
| --- | --- |
| `prepare.c` | 从 `sqlite3_prepare_v2()` 一类入口理解 prepare 阶段 |
| `tokenize.c` | 看 token 化以及 Parser 如何被驱动 |
| `parse.y` | 看 Lemon 语法规则和语法动作；`parse.c` 通常由它生成 |
| `select.c` | 看 `SELECT` 的规划结果怎样参与代码生成 |
| `insert.c`、`update.c`、`delete.c` | 对照写操作如何生成指令 |
| `vdbe.c` | 看 `sqlite3VdbeExec()` 如何解释 opcode |
| `vdbeaux.c` | 看 VDBE program 的构造、管理和辅助逻辑 |
| `vdbeapi.c` | 看 prepare 后的 statement API 如何驱动执行和取值 |
| `vdbeInt.h` | 看寄存器、游标和 VDBE 内部结构 |
| `btree.c` | 看表、索引和 BTree cursor 接口 |
| `pager.c` | 看页面缓存、事务、锁和日志相关机制 |
| `os.c` 与各平台 VFS | 看存储层如何落到操作系统能力 |

文件名和函数会随版本演化，阅读时应以当前 checkout 的源码和生成规则为准，不要只依赖二手文章中的行号。

## 一条可执行的阅读路线

### 1. 先固定一个查询

选择带主键条件的单表查询。它足以出现打开游标、定位记录、读取列和返回结果，又不会立刻陷入 join、聚合或子查询。

### 2. 用 `EXPLAIN` 得到实际指令

先把 opcode program 当作地图。记录每条指令修改了哪个寄存器、游标或程序计数器，以及跳转目标在哪里。

`EXPLAIN QUERY PLAN` 回答的是“采用什么访问计划”；`EXPLAIN` 展示的是“生成了什么 VDBE program”。两者不要混为一谈。

### 3. 在 `vdbe.c` 找 opcode

从 `OP_SeekRowid` 或 `OP_Column` 对应分支开始，观察：

- 指令参数怎样读取；
- 寄存器和游标怎样更新；
- 哪一步调用 BTree；
- 错误、跳转和资源释放怎样处理。

一次只跟一条指令，比分别通读所有大文件更容易建立可验证的认识。

### 4. 反向找代码生成点

搜索 `sqlite3VdbeAddOp*()` 及相应 opcode，找到 `select.c` 等文件中生成指令的位置。此时重点看“为什么选择这条指令”，而不是执行器“怎样实现它”。

### 5. 再向下进入 BTree 和 Pager

确认 VDBE 调用了哪个 BTree 接口后再进入 `btree.c`。只有当问题涉及页面获取、事务或锁时，才继续追到 `pager.c` 和 VFS。

这样可以避免一开始就在底层细节里失去主线。

### 6. 用调试器验证

在 prepare、opcode 执行和 BTree cursor 操作处设置少量断点，对照 `EXPLAIN` 的地址和运行时状态。源码阅读中的推断，最好都能被一次实际执行验证。

## 一次阅读应留下什么

读完一条链路后，建议把结果压成一张小卡片，而不是保存大段源码：

```text
输入 SQL：
表结构与索引：
SQLite 版本或 commit：
查询计划：
关键 opcode：
opcode 生成位置：
进入 BTree 的调用点：
运行时验证方式：
仍未确认的问题：
```

版本、表结构和索引必须记录，因为它们会直接改变查询计划和 opcode。把“源码观察”和“个人推断”分开写，也能避免以后把一次实验误当成 SQLite 的固定行为。

第一轮不必同时研究 join、聚合、事务和 WAL。等单表读取链路稳定后，可以一次只增加一个变量：先加普通索引，再看写操作，最后再进入事务与并发。每次都用新的 `EXPLAIN` 和断点结果修正理解。

## 阅读时值得记录的边界

源码笔记不必抄完整调用栈，可以围绕以下问题记录：

- 当前决定属于语法、规划、代码生成还是执行？
- 这个决定以什么数据结构传给下一层？
- 哪些状态由 statement 持有，哪些状态由 connection 或 pager 共享？
- 错误从哪里产生，又由哪一层转换或清理？
- 如果增加一种语法，哪些层应该变化，哪些层应保持不动？

这些问题比“某函数有多少行”更能暴露架构的真实边界。

## 可迁移的设计启发

### 1. 用稳定中间表示收敛耦合

VDBE program 让多种 SQL 语句共享同一个执行器。类似设计适用于输入形式经常变化、执行后端相对稳定的系统。

中间表示的价值不是多加一层，而是把原本的多对多依赖变成两组相对稳定的依赖。若上下游都只有一种且没有独立变化，引入虚拟机反而可能过度设计。

### 2. 分开“决定做什么”和“具体怎么做”

代码生成阶段选择操作及顺序，VDBE 执行这些选择，BTree 完成数据访问。决策与机制分开后，规划可以演化，而底层存储接口不必理解高级语法。

例如工作流系统可以先把声明式规则编译成有限的 command，再由统一执行器处理重试、状态和审计；执行器不需要理解原始配置文本。

### 3. 中间表示也是可观察性接口

`EXPLAIN` 能展示 VDBE program，因此“系统准备怎样执行”不再只存在于控制流中。一个可检查、可记录的中间表示，往往同时改善调试、测试和性能分析。

### 4. 把有状态资源集中到执行层

寄存器、游标、程序计数器和清理路径由 VDBE 统一管理，避免每种 SQL 各自维护一套执行状态。设计有状态引擎时，集中状态所有权通常比在多个业务分支里隐式传递更可靠。

### 5. 深层模块应隐藏真正复杂的知识

BTree 和 Pager 不是只做转发的“形式分层”：它们分别封装有序数据访问，以及页面、事务、锁和持久化知识。判断抽象是否值得保留，要看它隐藏了多少复杂性，而不是只看调用链是否变长。

## 容易产生的误解

- VDBE 不是查询优化器。访问路径的选择发生在更前面的规划和代码生成阶段。
- BTree 不是所有持久化职责的总称。页面缓存、事务日志、锁和 OS I/O 还在更下层。
- SQL 也不只是“字符串变成 token”。语法、名称解析、规划和代码生成共同完成从文本到程序的转换。
- 分层不意味着完全隔绝。性能、事务和错误处理仍会形成跨层约束，需要通过明确接口传递。
- 架构类比只能帮助定位职责，不能代替阅读当前版本的真实数据结构与调用关系。

## 当前结论

阅读 SQLite 并不是为了以后重写一个数据库，而是为了观察一个成熟系统如何管理变化：SQL 语法持续扩展，执行指令保持相对统一，存储层则专注于记录、页面和事务。

以后再回到源码时，先用一个查询和一份 `EXPLAIN` 输出恢复主线，然后分别追“谁生成这条指令”和“这条指令最终调用了什么”。这样既能深入，也不容易被细节淹没。
