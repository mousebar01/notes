# 项目文档编写指南：让读者能解释、修改和排障系统

> 本文基于 SQLite、Zulip、GitLab、Pro Git、Home Assistant 开发者文档的对比阅读，提炼适合中小工程项目的文档写作方法。完整版（含全部案例展开）存档于 `archive/topics/software-engineering/project-documentation-guide-完整版.md`。

## 核心原则（结论先行）

1. 先声明读者和阅读结果，再决定写什么。
2. 先建立少量、稳定的核心概念，再展开组件和细节。
3. 以请求、状态或数据的流动组织叙述，而不是以目录组织。
4. 不只说明"系统怎样做"，还解释"为什么只能/更适合这样做"。
5. 把约束、不变量、失败和恢复视为主流程的一部分。
6. 用具体例子验证模型，而不是用例子代替模型。
7. 通过渐进展开控制细节：总览、深入解释、参考信息各司其职。
8. 对页面数量保持克制：一个新名词 ≠ 一个新页面。
9. 把易变参数和稳定设计分开，降低文档失效速度。
10. 把代码、测试、配置和日志当作证据，不把文件路径当作正文骨架。

一条因果链概括全文：

```text
读者问题 → 核心模型 → 真实流程 → 设计约束 → 当前选择
  → 代价与不变量 → 失败和恢复 → 可验证的例子
```

## 优秀文档的 8 个共同点

**1. 开头建立阅读契约**。开头不是"本文介绍……"，而是排除不相关读者、说明读后获得什么能力、决定需要多少细节。写作前先写一句话："本文帮助【哪类读者】在【什么情境】下回答【什么问题】，不负责【哪些相邻问题】"——写不清楚这句话，页面边界也不会清楚。

**2. 先给心智模型，再给名词清单**。Pro Git 先讲"快照而非差异"，再讲命令；SQLite 先用一条管线（SQL → Tokenizer → Parser → Code Gen → VM → B-Tree → Pager）概括全系统。好模型：数量少、关系明确、能预测后续行为。

**3. 围绕流动和状态写，而不是围绕目录写**。Zulip 从"多个客户端持有旧状态如何保持一致"开始，而不是列事件文件。适合做主线的流：一次用户请求、一份数据的生命周期、一个后台任务的状态变化、一次失败到恢复的过程。目录树只回答"东西放哪"，回答不了"系统为什么这样运转"。

**4. Why 必须由真实约束支撑**。"为了可扩展性"不是理由。可信的 Why 来自：性能/延迟上限、一致性/事务要求、安全隔离、部署环境与故障模型、外部协议兼容、用户工作流、维护成本。无法证明的动机要写"当前能确认的约束是……"，不要替过去的作者编故事。

**5. 主动回答"为什么不用另一个方案"**。只有当：后来者很可能再次提出、存在真实取舍、影响边界或长期维护、有足够证据时，才值得记录替代方案。不要为每个微小决定编造三种备选。

**6. 把不变量、失败和恢复写进设计**。SQLite 的 Atomic Commit 先声明硬件假设，把删除 rollback journal 定义为可观察的 commit point，再分别推导电断电前/后的结果。高质量 How/Why 要同时回答：目标是什么、为什么简单方案不行、算法怎么工作、依赖什么不变量、代价在哪、测试怎么证明。

**7. 渐进展开，不一次倾倒细节**。信息顺序：一句话模型 → 一张能走通的主流程图 → 关键职责/边界/不变量 → 复杂分支与失败场景 → 易变参数与完整参考。对中小项目，前四层完全可以是一篇文档。

**8. 用实例证明模型，而不是堆砌实例**。Pro Git 先解释 content-addressable 对象模型，再用底层命令逐步创建 blob/tree/commit 让读者亲手验证。

## 五个项目各值得学什么

| 项目 | 可学点 |
|---|---|
| SQLite | 一条主干（SQL→Pager）解释完整系统，故障模型贯穿 |
| Zulip | 把架构写成可继续推理的约束（事件同步、last_event_id） |
| GitLab | 用部署现实约束未来设计（共享文件系统 vs K8s） |
| Pro Git | 先改造读者认知再教操作（Snapshots, Not Differences） |
| Home Assistant | 把"文档要好"变成可检查规则（Integration Quality Scale） |

## 页面不是知识的最小单位

- **四种写作模式是诊断工具，不是目录模板**（Tutorial / How-to / Explanation / Reference，详见 [项目文档编写](./项目文档编写.md) 的 Diátaxis 部分）；不要为一篇文章的每个段落各建一个页面。
- **新建页面的五个门槛**：读者任务是否独立？有没有可检查的输出？能否被链接/引用？维护成本是否可承受？删除后是否影响可读性？——全满足才值得独立成页。

## 从代码事实写 How 和 Why（五步法）

**第一步：定义读者要做出的判断**。不要从"我要介绍 X 模块"开始，而是明确"读者看完能判断什么"（如：新来源该接导入层还是检索层？一次任务能否安全重试？）。判断会自然暴露必须讲清的模型、边界和不变量。

**第二步：建立证据账本**。写正文前列表记录：声明 / 证据类型 / 可信度 / 还缺什么。证据优先级：可复现实验 > 协议与 schema > 完整调用链实现 > 配置部署 > 日志诊断 > 注释旧文档 > UI 表现或猜测。不要从 UI 症状反推内部原因，不要把"可能是"润色成设计动机。

**第三步：提取稳定模型**。找出核心名词与身份、输入输出与责任边界、状态机与生命周期、不能破坏的不变量、外部约束与失败模型、替代方案及代价。然后尝试用**一条不包含文件名和类名的流程**表达系统——做不到说明还停留在实现观察阶段。

**第四步：按因果链组织正文**：

```text
问题是什么？→ 现实约束？→ 当前选择？→ 实际怎么工作？
  → 哪些条件必须成立？→ 付出什么代价？→ 失败时怎么观察和恢复？
```

不必机械用七个标题，但不能长期只停留在"它是什么"。

**第五步：用正常路径 + 异常路径验证**。正常路径证明读者理解主流程；异常路径证明边界和不变量不是装饰（如：进程被取消时哪些事件仍可见、什么会持久化、能否重试）。文档说不清异常路径，往往意味着作者还没理解真正的所有权边界。

## 落地建议

- 对个人/中小项目：一个高质量 README（含 tutorial 性质 quickstart）+ 几篇按任务命名的 how-to + 一份 reference 已超过 80% 的项目。
- 两条硬标准：**可执行性**（quickstart 能在干净环境一次跑通，最好进 CI）；**不腐烂**（示例代码可测试的文档，质量自动高一档）。
- 删除测试：删掉这段用户还能完成任务吗？能，就不该放主文档。
