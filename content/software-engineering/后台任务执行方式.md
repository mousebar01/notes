# 后台任务执行方式

执行后台任务常见可以分成几类，从“最轻量”到“最工程化”大概是这样：

## 1. 进程内线程：`threading.Thread`

你现在项目用的就是这个。

请求进来后创建 `ActivityRun`，然后开一个 daemon thread 在后台跑任务，前端通过 Activity 状态轮询。

适合：

* 本地桌面应用
* 单用户项目
* 任务量不大
* 不想引入 Redis、worker、消息队列
* 任务失败后可以重新跑

优点是简单、轻量、依赖少。缺点是服务一重启线程就没了，不适合多进程、多实例，也不是真正可靠的任务队列。

你现在的方案属于：

```python
threading.Thread(target=run_task, daemon=True).start()
```

这是最直接的一类。

---

## 2. 进程内 asyncio 后台任务

如果后端本身是 async 框架，比如 FastAPI，可以用：

```python
asyncio.create_task(...)
```

或者 Starlette/FastAPI 的 `BackgroundTasks`。

适合：

* 轻量异步任务
* I/O 密集任务
* 发邮件、写日志、调用接口、同步小批量数据

比如：

```python
asyncio.create_task(sync_favorites())
```

优点是和 async 代码天然兼容。缺点和线程类似：进程重启任务就没了，也不适合长时间、重 CPU 的任务。

FastAPI 的 `BackgroundTasks` 更适合“请求返回后顺手做点事”，不太适合真正长任务。

---

## 3. 本地任务执行器 / 内置 worker

这是你项目下一步比较自然的方向。

不是直接到 Celery，而是在项目里抽一个统一的任务执行层，例如：

```python
task_executor.submit(
    name="tieba_favorite_sync",
    run_id=run.id,
    func=...
)
```

内部可以统一管理：

* 线程池
* 并发数
* 队列
* 任务取消
* 任务超时
* running/queued 状态恢复
* 任务类型注册
* 统一日志和进度更新

实现可以基于：

```python
concurrent.futures.ThreadPoolExecutor
```

或者：

```python
asyncio.Queue
```

这比直接到处 `threading.Thread(...).start()` 更可维护。

适合你现在这种本地单用户项目，尤其是未来有 OCR、贴吧批量导入、视频处理、AI 分析等多个后台任务时。

---

## 4. 独立子进程：`multiprocessing` / `subprocess`

如果任务比较重，特别是 CPU 密集型，比如：

* OCR
* 视频转码
* 图片处理
* 大文件解析
* 模型推理
* 批量压缩

就可以考虑用独立进程执行。

例如：

```python
subprocess.Popen(["python", "worker.py", "--run-id", run_id])
```

或者：

```python
multiprocessing.Process(target=run_task).start()
```

优点是隔离性更好，一个任务崩了不一定拖垮主服务；CPU 密集任务也不会被 Python GIL 限制得那么明显。

缺点是状态同步、日志收集、取消任务会更复杂。

---

## 5. 数据库轮询型任务队列

这种方式不一定需要 Redis。

可以把任务写进数据库：

```text
task_id | type | status | payload | created_at | started_at
```

然后项目启动一个 worker 循环：

```python
while True:
    task = db.pick_next_queued_task()
    run(task)
```

适合：

* 不想引入 Redis
* 但希望任务可持久化
* 服务重启后可以继续扫描 queued/running 状态
* 本地项目需要更可靠一点

优点是部署简单，只依赖现有数据库。缺点是吞吐和并发能力不如专业队列，但对本地桌面/单用户项目通常足够。

你现在的 `ActivityRun` 已经有点像这个方向了，只是还没有真正的 worker 调度层。

---

## 6. 专业任务队列：Celery / RQ / Dramatiq / Arq

这是 Web 后端里比较标准的后台任务方案。

典型架构是：

```text
Web API -> Redis/RabbitMQ -> Worker -> 更新数据库状态
```

常见选择：

* **Celery**：功能最全，适合复杂任务、定时任务、重试、分布式 worker。
* **RQ**：基于 Redis，简单易用，比 Celery 轻。
* **Dramatiq**：比 Celery 简洁，适合中等复杂度任务。
* **Arq**：async-first，适合 asyncio 项目，基于 Redis。

适合：

* 多用户
* 多实例部署
* 任务很多
* 需要重试、延迟任务、定时任务
* 需要 worker 独立扩容
* 任务不能因为 Web 服务重启就消失

缺点是引入额外组件，部署复杂度明显上升。对本地桌面项目来说，可能有点重。

---

## 7. 定时任务 / 调度器

如果任务不是由用户点击触发，而是定期运行，可以用：

* `cron`
* APScheduler
* systemd timer
* Celery beat
* Windows Task Scheduler

比如：

```python
scheduler.add_job(sync_favorites, "interval", hours=1)
```

适合：

* 每小时同步
* 每天清理缓存
* 定期扫描文件
* 定期生成索引

它解决的是“什么时候触发任务”，不是完整的任务执行可靠性。通常会和上面的线程池、数据库队列、Celery 等组合使用。

---

## 8. 外部服务 / 云任务

如果项目上云，还可以用：

* AWS SQS + Lambda
* Google Cloud Tasks
* Cloud Run Jobs
* GitHub Actions
* Kubernetes Jobs
* Temporal
* Prefect
* Airflow

这些更适合生产系统、数据管道、工作流编排，不太适合你现在这个本地桌面/单用户项目。
