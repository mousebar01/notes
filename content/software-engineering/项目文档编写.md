# 项目文档编写

这条笔记记录我对「项目文档该写到什么程度、该怎么组织」的理解。分两次形成：

- **第一次**（2026-07-24）关注**详细程度**：文档不必覆盖一切，应该按深度分层。
- **第二次**（2026-07-26）关注**组织维度**：发现我原本按「使用者 / 开发者」切分，这件事本身就是不满感的来源。

两部分都保留在下面。第二次的结论是第一次的上位框架——先决定按什么维度切，再决定每块写多细。

## 起点问题

> 我总觉得项目文档写得不好，我不知道标准在哪里，我一般是分成使用者和开发者两个层面去组织。

---

## 一、组织维度：按意图分，不按读者身份分

### 「使用者 / 开发者」这个切分是问题本身

按**读者身份**分类是文档最常见的陷阱：

1. **同一个人在不同时刻需要不同的东西。** 一个开发者早上是使用者（要先跑起来），下午是贡献者（要改代码）。按身份切，会把「同一个人此刻的需求」拆到两个地方。
2. **身份不能预测需求，意图才能。**「我是开发者」不告诉你他现在要什么；「我要接入 OpenAI」告诉你。
3. **最关键的**：身份分类不阻止你在同一篇文档里混合几种不同性质的内容。「使用者文档」里往往同时塞着教程、操作指南和参数表，读者要不断在「学习模式」和「查东西模式」之间切换——**这就是「说不出哪不好但就是觉得不好」的来源**。

### 标准：Diátaxis 四象限

Daniele Procida 提出，Django、Cloudflare、Ubuntu / Canonical、Gatsby 等都在用。它按**两个轴**切分，而不是按人：

| | 面向学习（study） | 面向工作（work） |
| --- | --- | --- |
| **实践性** | **Tutorial 教程** | **How-to 操作指南** |
| **理论性** | **Explanation 解释** | **Reference 参考** |

- **Tutorial 教程**：带新手完整走一遍，**保证成功**。目的是建立信心和熟悉感，不是解决真实问题——可以用玩具例子和假数据。
- **How-to 操作指南**：读者已经知道自己要什么，来找步骤。假设读者有基础，围绕真实目标组织。（下面第二部分「围绕任务写，不围绕文件写」说的就是这个。）
- **Reference 参考**：查阅用。参数表、API、配置项。枯燥是对的，完整和准确是唯一要求。
- **Explanation 解释**：讲 why、讲设计取舍、讲背景。**不含操作步骤。**

**核心规则只有一条：不要在一篇文档里混两种模式。** 教程里不要解释原理（打断学习流），how-to 里不要教基础，reference 里不要有教学口吻，explanation 里不要夹操作步骤。

### 最容易混的一对：Tutorial vs How-to

区别是**谁在负责**：

- 教程里**作者负责**，读者只要照做就一定成功；
- how-to 里**读者负责**，作者只提供路径。

所以教程可以（也应该）回避真实世界的复杂性，how-to 不行。

## 二、详细程度：写到什么程度就够了

> 这部分是 2026-07-24 的原始整理，起因是看 AstrBot 的文档结构。内容基本保留。

一个常见误区是**觉得「详细 = 专业」**，于是恨不得把每个函数、每个配置项、每个按钮都解释一遍，最后文档变成没人看的说明书。

像 AstrBot 这种成熟开源项目的文档，其实也不是追求「覆盖一切」，而是在不同层级提供不同深度的信息。它的结构更偏向：**让不同目的的人快速找到下一步要做什么**——安装、部署、接入、插件开发、API 等路径分开。[^1]

### 1. 首先回答：这个项目是什么？（必须）

目标：一个第一次看到项目的人，30 秒知道有没有兴趣。

包括：

- 项目解决什么问题
- 核心能力
- 适用场景
- 一个简单示例

例如：

> AstrBot 是一个基于 Python 的多平台 AI Agent 框架，可以连接 QQ、Telegram 等聊天平台，并通过插件扩展能力。

不用解释：

- 为什么选择 asyncio
- 内部消息怎么流转
- 每个模块怎么设计

这些属于开发文档。

### 2. 快速开始（必须）

这是用户最需要的部分。一般包含：

```text
安装
 ↓
配置
 ↓
运行
 ↓
看到效果
```

比如：

```bash
git clone xxx
pip install -r requirements.txt
python main.py
```

然后告诉用户：

> 如果看到 XXX 输出，说明运行成功。

**很多项目 README 最大的问题就是没有这个闭环。**

### 3. 核心概念（建议）

这里不要讲实现细节，只讲「脑中的模型」。比如一个机器人项目：

```text
用户消息
    ↓
平台适配器
    ↓
事件系统
    ↓
插件
    ↓
LLM
    ↓
回复
```

用户理解这个之后，后面看代码会容易很多。

### 4. 配置说明（按场景）

不要写成这样：

```text
config.json

aaa: 类型 string，默认 ""，作用 xxx
bbb: 类型 bool，默认 false，作用 xxx
ccc: ...
```

这种很容易变成垃圾文档。更好的方式是按任务组织：

**我想接入 OpenAI** → 改 `{"api_key": "xxx"}`

**我想修改端口** → 改 `{"port": 8080}`

**我想开发插件** → 去 `docs/plugin-development.md`

也就是说：**围绕任务写，不围绕文件写。**

> 补充（第二次）：这条对应 Diátaxis 里的 how-to。但要注意配置项本身仍然需要一份完整的 reference——按场景写的是入口，不是替代品。两者是不同象限，不该互相取代。

### 5. 开发者文档（项目壮大后再写）

比如架构设计、Plugin API、生命周期、Event 系统、数据库设计、二次开发。这些不是普通用户需要看的。

AstrBot 这类项目因为有插件生态，才需要进一步提供插件开发指南。[^2]

### 一个简单判断标准

问自己：**如果我是一个刚 clone 项目的人，我现在最想知道什么？**

| 时间点 | 想知道 | 对应文档 |
| --- | --- | --- |
| 第一分钟 | 这是什么？ | README |
| 第十分钟 | 怎么跑起来？ | Quick Start |
| 第一小时 | 怎么改？ | 配置文档 |
| 第一天 | 怎么扩展？ | 开发文档 |

### 详细程度可以这样分层

| 文档类型 | 详细程度 |
| --- | --- |
| README | 简洁，10 分钟看完 |
| 入门教程 | 带步骤 |
| 使用文档 | 覆盖常见需求 |
| API 文档 | 尽量完整 |
| 架构文档 | 面向贡献者 |

很多个人项目其实只需要前三个。

### 删除测试

**如果删除某段文字，用户依然能完成任务，那这段文字可能不该放在主文档里。**

❌

> main.py 第 35 行调用 BotManager 的 initialize 方法，该方法内部创建 EventLoop……

✅

> 启动后，系统会自动加载配置并初始化插件。

够了。

### 小结

项目文档的核心不是「把项目讲完」，而是：

> **帮助别人成功使用你的项目，并在需要的时候找到深入入口。**

AstrBot 这种大型项目文档多，是因为它面对用户、部署者、插件开发者、贡献者多个角色，不是因为每个项目都应该写这么厚。[^3]

如果是自己维护一个中小型开源项目，一个高质量 README + `docs/quickstart` + `docs/development` 就已经超过 80% 的项目了。

## 三、可以直接检查的硬标准

比框架更能拉开差距的两条，而且都是可验证的：

- **可执行性**：quickstart 能不能在干净环境里被一个陌生人**一次跑通**。这是唯一真正客观的文档质量指标。理想状态是放进 CI 定期跑。
- **不腐烂**：文档质量最大的杀手不是写得差，是过期。**示例代码能被测试**的项目，文档质量自动比别人高一档。

加上前面两部分的：

- **删除测试**：删掉这段用户还能完成任务吗？能，就不该放主文档。
- **模式测试**：这一段是四象限里的哪一种？**答不上来、或者同时是两种，就是要拆的地方。**

## 落地建议

不要一上来就建四个目录，那是过度工程。**Diátaxis 是诊断工具，不是目录模板。**

实际做法：拿现有文档逐段跑一遍「模式测试」，先把混在一起的拆开，再考虑要不要建目录。

对个人项目，通常够用的是：一个高质量 README（含 tutorial 性质的 quickstart）+ 几篇按任务命名的 how-to + 一份 reference。Explanation 可以等真的有人问「为什么这么设计」时再写。
