# 缓存与 CDN 设计

缓存通过保存可复用结果减少重复下载、计算和数据库访问。它本质上是用空间和一致性管理成本换取更低延迟与更高吞吐。

## 缓存层次

```text
用户
  -> 浏览器缓存
  -> CDN 边缘节点
  -> Web / API 服务器缓存
  -> Redis 等共享缓存
  -> 数据库或源站
```

| 层次 | 常见内容 | 主要收益 | 主要风险 |
| --- | --- | --- | --- |
| 浏览器 | CSS、JS、图片、字体 | 避免同一用户重复下载 | 用户持有旧版本 |
| CDN | 静态资源、下载文件、部分 HTML | 就近访问、分担源站流量 | 节点失效不同步 |
| 服务器 | 页面、API 响应、计算结果 | 减少重复业务计算 | 多实例一致性 |
| 共享缓存 | 查询结果、session、热点数据 | 减少数据库压力 | 穿透、击穿、陈旧数据 |

缓存设计首先要回答：缓存什么、缓存在哪里、如何命中、何时失效，以及缓存不可用时回到哪里。

## Web 静态资源策略

一般原则是：入口文档短缓存，可变资源带版本，不变资源长缓存。

| 资源 | 推荐思路 |
| --- | --- |
| HTML | 短缓存或每次复验，确保能引用最新资源 |
| 带 hash 的 CSS / JS | 长缓存，并使用 `immutable` |
| 图片、字体 | 稳定资源可长缓存；内容变化时换 URL |
| API 响应 | 根据业务新鲜度、用户和权限谨慎决定 |

带内容 hash 的文件名：

```text
app.a8f3c9.js
style.7fd21a.css
```

内容变化会生成新 URL，浏览器和 CDN 会自然请求新资源。这比始终覆盖 `/app.js` 更容易安全地使用长缓存。

Nginx 静态资源示例：

```nginx
location ~* \.(css|js|png|jpg|jpeg|gif|webp|svg|ico|woff2?)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

只有资源 URL 随内容变化时，才适合直接使用这类长缓存策略。

## 常见 Cache-Control 语义

- `max-age=<seconds>`：资源在指定时间内可以直接复用。
- `no-cache`：允许保存，但使用前必须向服务器复验。
- `no-store`：不要保存响应，适合敏感内容。
- `public`：共享缓存可以保存。
- `private`：只允许用户侧私有缓存，不应进入共享缓存。
- `immutable`：有效期内资源内容不会变化。

这些指令必须结合数据敏感性和鉴权方式使用。带用户信息的响应不能因为追求命中率而进入公共缓存。

## 内容更新与失效

缓存最难的问题不是写入，而是让旧数据按预期失效。

### URL 版本化

静态资源优先使用文件名 hash；查询参数也能改变缓存 key，但工程上通常不如内容 hash 稳定。

### 主动删除

业务数据更新后删除对应页面、API 或查询缓存：

```text
更新数据库
  -> 删除相关缓存 key
  -> 下次读取重新生成
```

这是常见的 cache-aside 思路。删除失败、并发读写和事务边界仍需单独处理。

### TTL

即使有主动失效，也应设置合理 TTL，避免遗漏事件后数据永久陈旧。TTL 应由“业务最多能接受多久旧数据”决定，而不是统一设置一个固定值。

### CDN 刷新

紧急更新或无法更换 URL 时，可以刷新指定 URL 或目录。全站刷新代价更高，通常只作为特殊操作。

## CDN 的位置

CDN 把资源缓存在靠近用户的边缘节点：

```text
首次请求：用户 -> CDN -> 源站
后续命中：用户 -> CDN
```

它主要解决网络距离和源站流量问题；服务器缓存主要解决业务计算和数据库访问问题。两者可以同时存在，但失效策略必须贯穿 CDN、源站和数据缓存，不能只清一层。

## 设计检查清单

1. 缓存 key 是否包含租户、用户、语言和权限等必要维度？
2. 数据更新后哪些层需要失效？
3. 最长允许返回多旧的数据？
4. 缓存未命中或不可用时是否能安全回源？
5. 热点 key 失效时是否会同时压垮数据库？
6. 敏感响应是否错误地标记为公共缓存？
7. 是否能观察命中率、回源量、陈旧数据和刷新失败？

一句话总结：缓存不是简单“存一份”，而是在性能、数据新鲜度、隔离边界和故障回退之间做明确取舍。
