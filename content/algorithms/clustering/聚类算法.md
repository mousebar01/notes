# 当前 memcell 聚类实现

这篇记录当前工程中 memcell 聚类逻辑的代码理解。它不是 KMeans 一类预先指定类别数量、反复迭代到收敛的算法，而是一次**全量重建、按时间顺序在线归并**的过程。

## 核心结论

```text
Markdown entry 变化
  -> cascade 更新 memcell 表
  -> 如果 cell 有变化，调用 _refresh_clusters()
  -> 全量读取 memcell
  -> 按 (user_id, kind) 分组
  -> 每组按 created_at 从早到晚处理
  -> 相似则并入已有 cluster，否则新建 cluster
  -> 覆盖写回 cluster / cluster_member 快照
```

它不预设“必须分成几类”。类别数量会随数据自然增长：相似内容越多，合并越多；主题越分散，新建的 cluster 越多。

## 一个直观例子

假设同一用户有这些 `episode` cell：

```text
A: 我在设计记忆系统
B: Markdown 应该作为事实源
C: LanceDB 只做检索索引
D: 周末想去爬山
E: 明天要面试
F: 记忆系统里 OME 怎么做
```

按时间顺序处理时：

```text
A -> 没有已有 cluster，新建 cluster_1: [A]
B -> 与 cluster_1 相似，并入: [A, B]
C -> 与 cluster_1 相似，并入: [A, B, C]
D -> 与已有 cluster 都不相似，新建 cluster_2: [D]
E -> 与已有 cluster 都不相似，新建 cluster_3: [E]
F -> 与 cluster_1 相似，并入: [A, B, C, F]
```

为了理解，可以把结果叫作“记忆系统设计”“爬山计划”和“面试”。但当前代码不会生成这样的主题名，`label` 只是：

```text
"{kind} cluster"
```

## 完整处理过程

### 1. 每次都是全量重建

`_refresh_clusters()` 会读取当前所有 cell：

```sql
SELECT cell_id, user_id, kind, text, created_at, vector_json FROM memcell
```

因此只要有 cell 发生变化，当前实现就会重新处理整张 `memcell` 表，而不是只更新 changed cells。

### 2. 先按用户和类型隔离

读取结果先按下面的键分组：

```text
(user_id, kind)
```

例如这些组会分别聚类：

```text
(default_user, episode)
(default_user, atomic_fact)
(default_user, memcell)
(default_user, user_profile)
(default_user, agent_case)
```

所以不同用户不会混在一起，`episode` 和 `agent_case` 也不会混在一起。

### 3. 每个 cell 先变成临时 cluster

每组内部按 `created_at` 排序。单个 cell 进入算法时会被包装为：

```python
Cluster(
    id=f"cluster_{cell_id}",
    centroid=cell_vector,
    count=1,
    last_ts=created_at_ms,
    preview=[text[:200]],
    members=[cell_id],
)
```

如果它不能并入已有 cluster，就直接成为一个新 cluster。此时 cluster id 由该类第一条 cell 的 id 派生。

### 4. 普通类型走几何归并

普通类型使用 `cluster_by_geometry()`，将 incoming cell 的向量与已有 cluster 的中心点比较：

```text
cosine(incoming.centroid, existing_cluster.centroid)
```

并入需要同时满足：

```text
相似度 >= 0.65
abs(incoming.last_ts - cluster.last_ts) <= 7 天
```

`cluster.last_ts` 会在合并后更新为最新成员的时间。因此这个 7 天窗口是相对 cluster 的最近活动时间，而不是永远相对第一条成员。

若没有 cluster 同时满足相似度和时间条件，就新建一类。

### 5. 合并会移动中心点

假设已有 cluster 有 3 个成员，新 cell 进入后会重新计算加权平均中心：

```text
new_centroid =
  (old_centroid * old_count + incoming_centroid * incoming_count)
  / (old_count + incoming_count)
```

单个 incoming cell 的 `count` 默认为 1。合并还会更新：

```text
count
last_ts
preview
members
```

其中 `preview` 只保留最后 5 个片段：

```python
preview=(existing.preview + new.preview)[-preview_cap:]
```

`members` 不截断，会保留完整成员列表。

### 6. 结果与处理顺序有关

算法按 `created_at` 从早到晚处理，早期形成的中心会影响后续 cell 的归属：

```text
A 先建立 cluster
B 并入 A
C 再与 AB 的新中心比较
```

这不是把 A、B、C 放在一起反复优化到全局最优。因此相同数据如果处理顺序变化，可能得到不同结果。

### 7. agent_case 有单独路径

`agent_case` 在有 LLM provider 时使用 `cluster_by_llm()`：

```text
先按向量找 top-30 候选 cluster
  -> top1 similarity >= 0.85：直接并入
  -> 否则：让 LLM 判断并入某个候选，或返回 new
```

这条路径没有普通几何聚类的 7 天时间窗，主要依赖向量召回和 LLM 对任务经验是否同类的判断。它能处理语义模糊的 case，但会增加 token 消耗和输出不确定性。

## 结果如何落盘

聚类完成后，每个结果通过 `upsert_cluster(...)` 写入 `cluster` 表。主要字段包括：

```text
cluster_id
owner_id
kind
label
centroid_json
last_ts
preview
```

成员关系写入 `cluster_member`。更新时会先删除这个 cluster 原有的 members，再插入本轮结果：

```sql
DELETE FROM cluster_member WHERE cluster_id=?
```

最后调用：

```python
delete_clusters_not_in(active_cluster_ids)
```

删除本轮没有生成的旧 cluster。因此 `cluster` 和 `cluster_member` 保存的是当前快照，不是历史日志。

当前还有两个值得注意的细节：

- `cluster_member.score` 写入时统一为 `1.0`，目前不能代表真实相似度，按 score 排序也没有实际区分度。
- `preview` 是有上限的展示片段，`members` 才是完整成员关系。

## 派生状态与重复聚类

cluster 是可以从 memcell 重建的派生产物，不是事实源。Markdown 仍然是 source of truth。

当前 episode entry 会同时派生：

```text
kind=memcell
kind=episode
```

由于聚类按 `kind` 隔离，同一批文本可能在 `memcell` 和 `episode` 下分别聚类，得到两组相似结果。这不是两组独立事实，而是派生结构中的重复计算。

## 当前实现的取舍

优点：

- 不需要预先指定类别数量。
- 新主题可以自然形成新 cluster。
- 普通类型只用向量计算，不消耗 LLM token。
- cluster 可以从 Markdown / memcell 全量重建。

局限：

- cell 变化会触发全量重聚类，数据量增长后成本会变高。
- 在线归并是顺序敏感的，不保证全局最优。
- 几何聚类效果依赖 embedding、`0.65` 阈值和 7 天窗口。
- label 只是通用占位符，没有主题命名能力。
- `agent_case` 的 LLM 路径可能增加成本和不稳定性。
- `memcell` 与具体 kind 可能重复聚类。

## 一句话总结

```text
当前聚类会全量读取 memcell，按 user/kind 分组后依 created_at 顺序在线归并；普通类型用 cosine 和时间窗决定是否并入，agent_case 可交给 LLM 判断，最终覆盖写入 SQLite 中的 cluster 快照。
```
