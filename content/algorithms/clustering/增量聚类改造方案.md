# 增量聚类改造方案

这份方案用于把 CluStream 的 `online micro-cluster` 思想裁剪到 Mira 记忆系统中。

要解决的核心问题只有一个：

```text
当前：cell 变化 -> 全量读取所有 memcell -> 全量重聚类
目标：cell 变化 -> 只更新受影响 cluster
```

目标不是完整复现 CluStream，而是以尽量小的改动获得可增量维护、可检查、可重建的聚类状态。

## 1. 设计结论

第一版采用 `BIRCH-style Online Micro-Cluster`：

```text
新 MemoryCell 进入
  -> 在同 owner_id + kind 下找最近 cluster
  -> 用 cosine 判断是否吸收
  -> 吸收时增量更新 CF
  -> 不满足阈值时新建 cluster
```

借用 BIRCH 的是 `Clustering Feature`（CF）统计量，不实现完整 CF Tree：

```text
N  = 成员数量
LS = 向量线性和
SS = 向量平方范数和
```

关键决策：

1. 日常路径只增量更新受影响 cluster。
2. 相似度用 embedding 更适合的 cosine，不用欧氏半径作主阈值。
3. 删除和修改优先用 CF 扣减；状态异常时才局部重算。
4. cluster 是派生状态，不写 Markdown，可以随时从 memcell 重建。
5. 保留全量 `rebuild_clusters()`，用于迁移、维护和算法升级。
6. 第一版不做 snapshot、macro-kmeans、自动拆分和默认 LLM refine。

概念映射如下：

| CluStream / BIRCH | Mira |
| --- | --- |
| data point | `MemoryCell` |
| micro-cluster | `cluster` |
| micro-cluster member | `cluster_member` |
| macro-cluster | OME 派生出的 profile / skill / idea cell |
| BIRCH CF | `N / LS / SS / centroid` |

## 2. 当前问题与改造边界

当前 `_refresh_clusters()` 会读取全部 memcell，按 `(user_id, kind)` 分组并重聚类，再覆盖写入 cluster。主要问题是：

1. 任意 cell 变化都会触发全量计算。
2. `agent_case` 的 LLM 聚类和全量刷新叠加后，token 成本不可控。
3. `cluster_member.score` 固定为 `1.0`，不能反映真实相似度。
4. `memcell` 和 `episode` 可能形成内容相近的镜像 cluster。
5. cluster 没有明确的算法与 embedding 版本，迁移边界不清楚。

第一版改造范围：

```text
新增 IncrementalClusterer
让 replace_cells_for_entries() 返回变化明细
cascade 默认调用增量更新
保留全量 rebuild_clusters()
cluster 存储 CF 和版本字段
cluster_member.score 写真实 cosine
```

默认参与聚类的 kind：

```python
CLUSTERABLE_KINDS = {
    "episode",
    "atomic_fact",
    "foresight",
    "agent_case",
    "agent_skill",
    "idea_capture",
}
```

暂不默认聚类：

- `memcell`：它是 boundary 追踪和检索对象，又可能由 episode 派生；同时聚类容易重复。
- `user_profile`：它已经是高层派生结果，继续聚类可能形成自我强化。

## 3. CF 与 cosine 公式

设一个 cluster 的成员向量为 `x1, x2, ..., xn`：

```text
N  = n
LS = x1 + x2 + ... + xn
SS = ||x1||^2 + ||x2||^2 + ... + ||xn||^2
centroid = LS / N
```

即使 embedding 已归一化、通常有 `SS ≈ N`，仍保留 SS，用于检查离散度和异常状态。

### 3.1 新增、删除与修改

吸收新向量 `x`：

```text
N'  = N + 1
LS' = LS + x
SS' = SS + ||x||^2
centroid' = LS' / N'
```

新建 cluster：

```text
N = 1
LS = x
SS = ||x||^2
centroid = x
```

删除旧向量 `x`：

```text
N'  = N - 1
LS' = LS - x
SS' = SS - ||x||^2
centroid' = LS' / N'
```

当 `N' <= 0` 时直接删除空 cluster。

数学上，同一 cluster 内修改可以写成：

```text
LS' = LS - old_x + new_x
SS' = SS - ||old_x||^2 + ||new_x||^2
```

但工程上必须按“删除旧 cell，再重新分配新 cell”处理，因为修改后的内容可能属于另一个 cluster。

两个 cluster 需要合并时，CF 可以直接相加：

```text
N = N1 + N2
LS = LS1 + LS2
SS = SS1 + SS2
centroid = LS / N
```

### 3.2 吸收判断与观测指标

对新 cell 向量 `x`：

```text
score = cosine(normalize(x), normalize(centroid))
```

当 `score >= threshold(kind)` 时吸收，否则新建 cluster。

CF 还可以给出方向一致性：

```text
cohesion = ||LS|| / N
dispersion = 1 - cohesion
```

第一版只把它们用于观测和验收，不作为硬拒绝规则。需要兼容 BIRCH 欧氏语义时，也可以计算：

```text
radius^2 = SS / N - ||LS / N||^2
```

但 embedding 检索主路径仍以 cosine 为准。

## 4. 数据表与接口

### 4.1 `cluster`

保留现有字段，并增加 CF 与版本信息：

| 字段 | 含义 |
| --- | --- |
| `cluster_id` | cluster 主键 |
| `owner_id` | 用户或 agent 作用域 |
| `kind` | cell 类型 |
| `label` | 可读标签 |
| `centroid_json` | 当前中心向量 |
| `member_count` | CF 的 N |
| `last_ts` | 最新成员时间 |
| `preview` | 最近内容的短预览 |
| `created_at` | cluster 创建时间 |
| `updated_at` | 最近维护时间 |
| `ls_vector_json` | CF 的 LS |
| `ss_scalar` | CF 的 SS |
| `cohesion` | `||LS|| / N` |
| `dispersion` | `1 - cohesion` |
| `embedding_model` | 生成向量的模型版本 |
| `algorithm_version` | 如 `micro_cluster_v1` |

建议新增字段使用可迁移的默认值，但旧 cluster 在回填 CF 前不能直接进入增量路径。

### 4.2 `cluster_member`

复用现有字段：

| 字段 | 含义 |
| --- | --- |
| `cluster_id` | 所属 cluster |
| `member_type` | 当前写 `memcell` |
| `member_id` | 兼容现有成员标识 |
| `cell_id` | 对应 memcell |
| `score` | 成员分配或最近校准时的 cosine |

新建 cluster 的第一个成员 `score = 1.0`。日常吸收写成员与吸收前 centroid 的 score；局部重算时，可以按新 centroid 校准该 cluster 的所有 score。因此它不是每次中心移动后都实时更新的指标，消费者若要求“相对当前 centroid”的精确值，应在读取时重算。

### 4.3 `CellReplaceResult`

`replace_cells_for_entries()` 不能只返回 `changed: bool`，还要让 cascade 知道具体变更：

```python
@dataclass(frozen=True)
class CellReplaceResult:
    changed: bool
    changed_cells: list[MemoryCell]
    deleted_cell_ids: list[str]
```

`changed_cells` 需要包含 text、kind、时间和 vector；否则聚类层还要重复查询或重新 embedding。

## 5. 日常增量流程

统一入口：

```python
clusterer.update(
    changed_cells=replace_result.changed_cells,
    deleted_cell_ids=replace_result.deleted_cell_ids,
)
```

执行顺序固定为：

```text
删除旧 cell -> 分配 changed cell -> 修复异常 cluster -> 提交
```

### 5.1 删除

对每个 `deleted_cell_id`：

1. 通过 `cluster_member` 找到旧 cluster，并读取旧 cell 向量。
2. 从 `N / LS / SS` 扣除该向量。
3. 删除成员关系。
4. `N' <= 0` 时删除 cluster；否则更新 centroid 和观测指标。
5. 若删除的是最新或预览成员，只在该 cluster 内刷新 `last_ts / preview`。

`last_ts` 取剩余成员最大的 `created_at`。`preview` 取最近 5 条、每条最多 200 字，最终限制为 500 字；它们是展示字段，不应让删除退化成全量重聚类。

### 5.2 新增

对每个 changed cell：

1. kind 不在 `CLUSTERABLE_KINDS` 时跳过。
2. 只读取相同 `owner_id + kind + embedding_model + algorithm_version` 的 cluster。
3. 按时间窗口过滤候选，计算 cell 与 centroid 的 cosine。
4. 最高分达到该 kind 的阈值时吸收，并更新 CF。
5. 没有合格候选时，以该 cell 新建 cluster。
6. 写入 `cluster_member` 和真实 score。

候选必须在同一 owner 作用域内，避免用户或 agent 之间串数据。

### 5.3 修改

Markdown entry 修改后，旧 cell 的内容、hash 和 embedding 都可能变化。因此处理为：

```text
remove(old_cell)
assign(new_cell)
```

这样同时覆盖“仍留在原 cluster”“转移到其他 cluster”和“新建 cluster”三种情况。

同一批 entry 可能同时包含删除和新增，数据库更新与 cluster 更新应在明确的事务边界内完成；失败后不留下只更新 memcell、未更新 cluster 的半状态。

## 6. 异常恢复

`recompute_cluster(cluster_id)` 是局部 repair fallback，不是日常主路径。以下情况触发：

1. `member_count` 与 `cluster_member` 数量不一致。
2. `ls_vector_json` 缺失、不可解析或维度不一致。
3. `ss_scalar < 0`，或 CF 与 centroid 明显不一致。
4. `cluster_member` 指向不存在的 memcell。
5. 维护命令显式要求 repair。

局部重算只读取受影响 cluster 的成员：

```text
JOIN cluster_member 和 memcell
  -> 丢弃无 cell、无向量或维度错误的无效成员
  -> 无有效成员时删除 cluster
  -> 否则重算 N / LS / SS / centroid
  -> 刷新 cohesion / dispersion / last_ts / preview
  -> 按新 centroid 重写 member score
```

第一版不自动拆分低内聚 cluster。若怀疑成员归属已经污染，使用全量重建；自动拆分需要独立的簇内算法，不应混入首次改造。

cell 没有 `vector_json` 时不能参与聚类。cascade 顺序必须保证：

```text
upsert cell -> embedding -> 写 vector/LanceDB -> cluster assign
```

embedding 失败时，本次 job 应失败或重试，不能创建无向量 cluster。

## 7. 冷启动与迁移

### 7.1 冷启动

memcell 已有向量而 cluster 为空时，第一个可聚类 cell 直接新建 cluster；之后继续走普通增量分配，不需要特殊分支。

### 7.2 旧库回填

旧库只有 centroid 和成员关系、没有 CF 字段时，升级流程是：

```text
执行 schema migration
  -> 按 cluster_member JOIN memcell.vector_json
  -> repair_clusters() 回填 N / LS / SS / centroid
  -> 校验后开启增量路径
```

无法修复的 cluster 可以删除并由 `rebuild_clusters()` 重建，因为 cluster 本身不是事实源。

### 7.3 版本不一致

当前配置与 cluster 的 `embedding_model` 或 `algorithm_version` 不一致时，不允许混合增量更新。以下变化都应触发全量重建：

- embedding 模型或向量维度变化；
- threshold / time window 的语义发生变化；
- 聚类算法从 `micro_cluster_v1` 升级到新版本；
- 大规模手工修改 Markdown，无法可靠获得逐 cell diff。

## 8. 策略参数

第一版使用固定配置，先通过真实数据验收，再考虑自适应阈值：

| kind | cosine threshold | time window |
| --- | ---: | ---: |
| `episode` | 0.65 | 7 天 |
| `atomic_fact` | 0.70 | 30 天 |
| `foresight` | 0.70 | 30 天 |
| `agent_case` | 0.70 | 90 天 |
| `agent_skill` | 0.75 | 365 天 |
| `idea_capture` | 0.68 | 90 天 |

这些值是起始配置，不是算法真理。验收时至少观测：

- cluster 数量和大小分布；
- 分配 score 的分位数；
- cohesion / dispersion；
- 新建 cluster 比例；
- 人工抽样的误合并与误拆分。

阈值调整会改变成员归属，调整后应提升 `algorithm_version` 或执行全量重建，不能让新旧规则长期混用。

## 9. 全量重建与派生状态

保留 `rebuild_clusters()`：

```text
清空 cluster_member / cluster
  -> 读取所有 clusterable memcell
  -> 按 created_at、cell_id 稳定排序
  -> 逐个调用与日常路径相同的 assign_cell()
```

全量重建和日常分配必须复用同一套 policy，避免两条实现产生不同结果。

同时区分两个维护动作：

```text
repair_clusters()  = 不改变成员归属，只校准统计量和元数据
rebuild_clusters() = 清空派生状态，重新决定成员归属
```

Markdown 保留 episode、fact、foresight、case、skill 等人可读事实源；`cluster / cluster_member / CF` 留在 SQLite。这样算法变化时可以重建，也不会让文件数量随派生状态增长。

## 10. LLM 与 OME

第一版默认关闭 LLM 聚类。先把确定性的增量路径做稳，再考虑只在相似度灰区启用 refine，例如：

```text
score >= 0.78          -> 直接吸收
score <= 0.50          -> 直接新建
0.50 < score < 0.78    -> 可选 LLM refine
```

LLM refine 只能由显式配置或维护任务开启，避免 token 成本进入普通 cascade。

OME 的读取接口保持不变：

```text
cluster -> cluster_member -> memcell
```

这次改造只改变 cluster 的维护方式，不改变 profile / skill 抽取链路。

## 11. 文件改造点

建议新增：

```text
src/mira/plugins/memory/clustering.py
```

职责包括：

```text
IncrementalClusterer
ClusterPolicy / CLUSTERABLE_KINDS
update_clusters() / assign_cell()
recompute_cluster() / repair_clusters()
rebuild_clusters()
```

需要修改：

| 文件 | 改造点 |
| --- | --- |
| `db.py` | 扩展 `CellReplaceResult`；增加候选查询、CF 更新和 repair 辅助方法；迁移 cluster 字段 |
| `cascade.py` | 用增量更新替换默认 `_refresh_clusters()`；保留显式 rebuild |
| `service.py` | rebuild 时调用全量重建；inspect 显示算法、模型和一致性状态 |

实现时应让聚类层依赖小而明确的数据库接口，不把 SQL、policy 和 cascade 调度重新揉进一个函数。

## 12. 验收标准与后续

第一版完成后需要验证：

1. 修改一个 Markdown entry，只处理该 entry 对应的 cells。
2. 新增、删除或修改一个 cell，只影响相关 cluster。
3. 删除成员会扣减 CF，空 cluster 会删除。
4. 修改后的 cell 可以迁移到另一个 cluster。
5. `cluster_member.score` 不再全部是 `1.0`。
6. `memcell` 和 `user_profile` 默认不参与聚类。
7. CF 异常只触发受影响 cluster 的局部重算。
8. embedding 或算法版本不一致时拒绝混合更新。
9. 全量 rebuild 可重复执行，并通过同一 assign policy 得到稳定结果。
10. 检索主路径不受影响，OME 仍能读取 cluster 候选。
11. 增量结果与同配置的全量重建结果在抽样数据上可对照。
12. 日常 cascade 不再触发默认 LLM 聚类。

后续版本再考虑 pending / outlier buffer、自动拆分、cluster snapshot、pyramidal time frame 和 evolution analysis。它们有独立价值，但不应扩大第一版的实现面。

一句话总结：Mira 第一版不完整复现 CluStream，而是吸收它的 online micro-cluster 思想，让日常变化只更新受影响 cluster，必要时仍可从 Markdown 和 memcell 全量重建。
