# AI Coding 的可观察调试方法论

AI Coding 的瓶颈不只是生成代码，而是让 AI 能在真实反馈中定位和修正问题。目标不是要求模型一次写对，而是建立一个可执行、可观察、可验证的调试闭环。

## 调试闭环

```text
理解目标
  -> 修改代码
  -> 运行真实检查
  -> 观察错误、日志和界面状态
  -> 缩小问题范围
  -> 再次修改与验证
```

代码需要提供稳定的调用入口，AI 才能获得环境反馈。早期可以直接使用 CLI、测试命令或后端接口；只有出现跨工具、跨进程的标准化需求时，再考虑 MCP 等协议层。

## 观察信息应该按问题增加

可观察性不等于预先加入大量日志。更有效的方式是让日志和诊断成为调试动作：

- 输出关键输入、返回值和执行路径。
- 记录接口状态、错误类型和重试原因。
- 暴露必要的中间状态，而不是倾倒全部上下文。
- 问题解决后删除临时噪音，保留真正有长期价值的诊断点。

判断标准是：这些信息能否帮助下一步行动，而不是日志数量是否足够多。

## Mock 与真实环境

不同验证层解决不同风险：

| 验证方式 | 适合发现的问题 |
| --- | --- |
| 单元测试 / Mock | 纯逻辑、映射、边界输入和局部失败 |
| 集成测试 | 模块契约、数据库、文件和外部服务适配 |
| 真实运行 | 权限、网络、缓存、浏览器、终端和环境差异 |

Mock 能降低反馈成本，但不能证明真实环境正确。关键链路最终必须在接近实际使用的环境中运行。

前端还需要额外观察：浏览器日志、网络请求、DOM、截图、交互路径和不同视口。只读源码无法证明页面真的可用。

## 人与 AI 的职责

AI 适合完成执行、观察、局部定位和重复验证；人需要保留目标、风险和关键设计决定。

在实现前，可以先通过 [Grill With Docs](./Grill%20With%20Docs%20需求澄清方法.md) 暴露假设和约束。成熟项目中也应优先让 AI 在现有架构里做局部适配，而不是脱离上下文重新设计一套系统。

## 选择 Prompt、Workflow 还是 Agent

- **Prompt / Chat**：探索性问题，需要推理但不需要自主执行。
- **Workflow**：步骤和判断条件稳定，可以确定性编排。
- **Agent**：需要多步决策、工具调用和根据反馈调整行动。

不要为了使用 Agent 而使用 Agent。确定性越强，越应该把行为下沉为测试、脚本或 workflow。

## 开关与消融

对检索、重排、压缩、自动修复等新机制保留可控开关，可以快速比较启用与关闭时的差异。消融的目标是回答：

```text
哪一部分真正改善了结果？
关闭它以后是否明显变差？
收益是否值得新增复杂度？
```

可观察性负责看见问题，开关和消融负责隔离原因。

## 最小实践清单

1. 让项目可以用稳定命令运行和检查。
2. 给 AI 提供必要的日志、错误、截图和状态。
3. 先跑快速测试，再跑真实关键链路。
4. 信息不足时增加针对性观察点。
5. 新机制提供回退开关和对照验证。
6. AI 无法继续时，再由人补充判断或改变设计。

一句话总结：AI Coding 的重点不是生成更多代码，而是让代码修改进入一个可观察、可验证、可持续修正的环境。
