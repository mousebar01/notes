# 知识图谱与图论基础

这篇从实体、关系、三元组和 Schema 开始理解知识图谱，再补充节点、边、路径、遍历等图论基础，最后把这些概念放回多模态 RAG 场景中。

## 知识图谱基础

知识图谱可以理解成一种**用“点”和“边”来组织知识的结构**。

最简单的形式是：

```text
实体 A —— 关系 —— 实体 B
```

比如：

```text
苹果公司 —— 创始人 —— 史蒂夫·乔布斯
北京 —— 首都属于 —— 中国
论文 A —— 使用方法 —— RAG
图片 3 —— 被解释于 —— 第 2.1 节文本
```

这类结构通常叫 **三元组**：

```text
(head, relation, tail)
头实体，关系，尾实体
```

例如：

```text
(苹果公司, 创始人, 史蒂夫·乔布斯)
(图 2, has_caption, “系统整体架构图”)
(文本块 13, explains, 图 2)
```

---

### 1. 知识图谱由什么组成？

核心有三个东西：**实体、关系、属性**。

#### 实体 Entity

实体就是图里的“点”。

可以是人、公司、地点、产品，也可以是文档里的元素。

```text
人：乔布斯、马斯克
公司：Apple、OpenAI
地点：北京、东京
概念：RAG、Transformer、知识图谱
文档元素：第 3 页、图 2、表 1、文本块 15
```

在多模态 RAG 里，实体不一定是现实世界概念，也可以是：

```text
PDF 文档
页面
章节
段落
图片
表格
公式
图表
caption
```

#### 关系 Relation

关系就是两个实体之间的连接。

```text
乔布斯 —— 创立 —— Apple
图 2 —— 位于 —— 第 4 页
文本块 13 —— 解释 —— 图 2
表 1 —— 支持 —— 结论 A
```

关系是知识图谱最核心的价值，因为它让知识不是一堆孤立文本，而是可以被“沿着关系查找”。

#### 属性 Attribute

属性是实体自己的信息，不一定指向另一个实体。

比如：

```json
{
  "entity": "图 2",
  "type": "image",
  "page": 4,
  "caption": "系统整体架构图",
  "bbox": [80, 300, 500, 620],
  "summary": "该图展示 Query → Retriever → Generator 的流程"
}
```

属性适合存放：

```text
名称
类型
页码
时间
坐标
摘要
来源文件
置信度
```

---

### 2. 三元组是什么？

三元组是知识图谱最常见的表达方式：

```text
主语 —— 谓语 —— 宾语
Subject —— Predicate —— Object
```

也可以叫：

```text
Head —— Relation —— Tail
```

例子：

```text
(Apple, founded_by, Steve Jobs)
(RAG, uses, Retriever)
(图 3, located_in, Page 5)
(TextChunk_12, references, Image_3)
```

三元组的好处是非常清晰，适合存储和查询。

比如你想问：

```text
TextChunk_12 引用了哪些图片？
```

就查：

```text
(TextChunk_12, references, ?)
```

---

### 3. Schema 是什么？

**Schema** 是知识图谱的“规则设计”或“数据模型”。

它规定：

```text
有哪些实体类型？
有哪些关系类型？
哪些实体之间可以连什么关系？
每种实体有哪些属性？
```

比如多模态文档知识图谱的 schema 可以是：

```text
实体类型：
Document
Page
Section
TextChunk
Image
Table
Formula
Caption
Entity

关系类型：
contains
located_in
has_caption
references
explains
supports
same_section_as
near
mentions
```

然后定义规则：

```text
Document contains Page
Page contains TextChunk
Page contains Image
Image has_caption Caption
TextChunk references Image
TextChunk explains Image
Table supports Claim
```

Schema 很重要，因为没有 schema，图谱会变得很乱。

比如同一个关系可能被写成：

```text
references
refers_to
mentions_figure
cites
```

如果不统一，后面检索会很麻烦。

---

### 4. 本体 Ontology 是什么？

**Ontology，本体**，可以理解成更高级、更严格的 schema。

它不仅规定实体和关系，还会规定概念层级、约束和逻辑关系。

例如：

```text
狗 是 动物
猫 是 动物
动物 是 生物
公司 是 组织
大学 是 组织
```

可以表示成：

```text
Dog subClassOf Animal
Cat subClassOf Animal
Animal subClassOf LivingThing
Company subClassOf Organization
University subClassOf Organization
```

在普通 RAG 项目里，不一定要做复杂 ontology。
但在医疗、金融、法律、科研领域，本体很有价值，因为这些领域概念关系比较严格。

比如医疗知识图谱：

```text
疾病 —— 有症状 —— 症状
药物 —— 治疗 —— 疾病
药物 —— 禁忌 —— 人群
检查 —— 诊断 —— 疾病
```

---

### 5. 知识图谱怎么存？

常见有三种方式。

#### 方式一：三元组表

最简单：

| head         | relation    | tail      |
| ------------ | ----------- | --------- |
| TextChunk_12 | references  | Image_3   |
| Image_3      | located_in  | Page_5    |
| Image_3      | has_caption | Caption_3 |

可以用 CSV、JSON、SQLite、PostgreSQL 存。

适合 PoC 和早期项目。

#### 方式二：图数据库

例如 Neo4j、NebulaGraph、JanusGraph。

图数据库适合做复杂关系查询，比如：

```text
查找和图 2 距离两跳以内的文本、表格和章节
```

Neo4j 的查询语言叫 Cypher，例如：

```cypher
MATCH (t:TextChunk)-[:REFERENCES]->(i:Image)
WHERE i.caption CONTAINS "架构"
RETURN t, i
```

#### 方式三：向量库 + 图结构混合存储

RAG 里最常见的是：

```text
向量库：负责语义检索
图数据库 / 关系表：负责关系检索
对象存储：保存图片、PDF、表格原文件
```

比如：

```text
Qdrant / Milvus / Elasticsearch：存 embedding
PostgreSQL / Neo4j：存 nodes 和 edges
MinIO / S3 / 本地文件：存图片和文档
```

---

### 6. 知识图谱怎么构建？

构建知识图谱通常有两条路线。

#### 路线一：人工设计 + 规则抽取

适合结构明确的数据。

比如文档 RAG：

```text
每个 PDF 是 Document
每一页是 Page
每个段落是 TextChunk
每张图片是 Image
每个表格是 Table
```

关系可以规则生成：

```text
Document contains Page
Page contains TextChunk
Page contains Image
Image has_caption Caption
TextChunk located_in Page
Image same_page_as TextChunk
```

这种关系比较可靠。

#### 路线二：模型抽取

用 NLP 模型、LLM 或 VLM 从内容里抽取实体和关系。

比如从句子：

```text
RAG 由检索器和生成器组成。
```

抽取：

```text
(RAG, consists_of, Retriever)
(RAG, consists_of, Generator)
```

从图像中抽取：

```text
(Image_3, contains, Retriever)
(Image_3, contains, Generator)
(Retriever, connects_to, Generator)
```

模型抽取更灵活，但可能出错，所以通常要给关系加上：

```text
confidence
source
evidence
method
```

例如：

```json
{
  "head": "TextChunk_13",
  "relation": "explains",
  "tail": "Image_2",
  "confidence": 0.87,
  "method": "llm_extraction",
  "evidence": "文本中出现“如图 2 所示”"
}
```

---

### 7. 图谱查询是什么？

知识图谱的强项是“沿关系找答案”。

比如：

```text
问题：图 2 被哪些文本解释？
```

查询：

```text
(TextChunk, explains, Image_2)
```

或者：

```text
问题：和第 4 页的表格相关的图片有哪些？
```

路径可能是：

```text
Table_1 located_in Page_4
Image_2 located_in Page_4
Table_1 same_section_as Image_2
```

再比如多跳查询：

```text
问题：支持结论 A 的图表在哪一页？
```

路径：

```text
Claim_A supported_by Table_1
Table_1 located_in Page_5
```

这就是图谱比普通文本搜索强的地方：
**它可以沿着实体和关系做多跳推理。**

---

### 8. 知识图谱和向量检索有什么区别？

二者不是替代关系，而是互补关系。

| 能力        | 知识图谱             | 向量检索          |
| --------- | ---------------- | ------------- |
| 擅长        | 显式关系、多跳路径、结构查询   | 语义相似、模糊匹配     |
| 不擅长       | 没有建边的隐含语义        | 精确关系和逻辑路径     |
| 查询方式      | 沿边查找             | embedding 相似度 |
| 例子        | A 支持 B，B 位于第 3 页 | “意思相近”的段落     |
| 在 RAG 中作用 | 扩展上下文、关系推理       | 召回相关内容        |

例如用户问：

```text
“这段结论是哪个图支持的？”
```

知识图谱好用，因为可以查：

```text
Claim_X supported_by Figure_Y
```

用户问：

```text
“系统性能有没有提升？”
```

向量检索好用，因为它能找到“准确率提高”“延迟降低”“指标改善”等语义相近内容。

所以混合架构一般是：

```text
关键词 / 实体识别 → 图谱检索
问题 embedding → 向量检索
两边结果合并 → rerank → 生成回答
```

### 9. 什么是图嵌入 Graph Embedding？

图嵌入是把图里的实体和关系变成向量。

例如：

```text
Apple → [0.12, -0.45, ...]
Steve Jobs → [0.35, 0.08, ...]
founded_by → [0.67, -0.21, ...]
```

这样可以用向量空间捕捉图上的关系。

常见图嵌入方法包括：

```text
TransE
RotatE
ComplEx
Node2Vec
GraphSAGE
GAT
```

在普通 RAG 里，不一定需要一开始就用复杂图嵌入。
更常见的是：

```text
文本内容做 embedding
图片摘要做 embedding
实体名称和关系描述做 embedding
图结构用数据库或关系表保存
```

---

### 10. 什么是多跳推理？

多跳推理就是不是一步找到答案，而是沿着多个关系走。

比如：

```text
乔布斯 —— 创立 —— Apple
Apple —— 发布 —— iPhone
iPhone —— 属于 —— 智能手机
```

问：

```text
“乔布斯创立的公司发布了什么智能手机？”
```

需要走多步：

```text
乔布斯 → Apple → iPhone → 智能手机
```

在多模态 RAG 里：

```text
TextChunk_13 references Image_2
Image_2 located_in Page_4
Page_4 belongs_to Section_2
Section_2 discusses RAG Architecture
```

问：

```text
“RAG 架构图在哪一页？”
```

可以沿图找到：

```text
RAG Architecture → Section_2 → Page_4 → Image_2
```

---

### 11. 知识图谱在多模态 RAG 里的作用

放到你关心的多模态 RAG 里，知识图谱主要解决这个问题：

> 文本、图片、表格、公式之间不是孤立的，应该显式建立关系。

比如：

```text
TextChunk_12 —— references —— Image_3
Image_3 —— has_caption —— Caption_3
Image_3 —— located_in —— Page_5
Table_2 —— supports —— Claim_7
Formula_1 —— defines —— Metric_Accuracy
```

这样查询时就可以：

```text
用户问题命中文本块
→ 沿 references 找到图片
→ 沿 same_section_as 找到表格
→ 把文本、图片、表格一起交给多模态模型
```

没有图谱时，系统可能只找到文本，漏掉图片和表格。

---

### 12. 一个最小知识图谱例子

假设一个 PDF 第 4 页有一段话和一张架构图：

```text
文本：如图 2 所示，系统由 Retriever、Reranker 和 Generator 组成。
图片：图 2，系统架构图。
```

可以构建：

```text
(Document_1, contains, Page_4)
(Page_4, contains, TextChunk_13)
(Page_4, contains, Image_2)
(Image_2, has_caption, Caption_2)
(Caption_2, text, "图 2：系统架构图")
(TextChunk_13, references, Image_2)
(TextChunk_13, mentions, Retriever)
(TextChunk_13, mentions, Reranker)
(TextChunk_13, mentions, Generator)
(Image_2, contains_entity, Retriever)
(Image_2, contains_entity, Reranker)
(Image_2, contains_entity, Generator)
(Retriever, flows_to, Reranker)
(Reranker, flows_to, Generator)
```

用户问：

```text
“Reranker 后面接什么？”
```

系统可以从图关系里找到：

```text
Reranker flows_to Generator
```

再结合文本和图片回答。

---

### 13. 实际项目里最重要的几个知识点

你只要先掌握这些就够了：

```text
1. 节点：图里的对象，例如人、公司、文本块、图片、表格。

2. 边：节点之间的关系，例如 located_in、references、explains、supports。

3. 三元组：head-relation-tail，是知识图谱最基本表达。

4. Schema：规定有哪些节点类型和关系类型。

5. 属性：实体或关系上的附加信息，比如页码、坐标、置信度、来源。

6. 构建：可以靠规则、NLP/LLM 抽取、VLM 图像理解。

7. 查询：沿关系找信息，支持多跳检索。

8. 图谱 + 向量：图谱负责显式关系，向量负责语义相似，二者结合最好。
```

---

一句话总结：

**知识图谱就是把知识从“文本堆”变成“实体—关系—实体”的网络。**
在多模态 RAG 里，它的核心作用是把 **文本块、图片、表格、公式、章节、页码** 显式连接起来，让检索不只靠语义相似，还能沿着结构关系找到相关证据。

## 图论基础

图（Graph）可以理解成一种**描述对象之间关系的数据结构**。它由两类基本元素组成：

```text
图 = 节点 + 边
Graph = Vertices / Nodes + Edges
```

比如：

```text
A —— B
```

这里 A、B 是节点，中间的线就是边。

---

### 1. 节点 Node / Vertex

**节点**表示一个对象、实体或状态。

例如在社交网络里：

```text
小明
小红
小李
```

在知识图谱里：

```text
RAG
知识图谱
图 2
第 4 页
文本块 13
```

在地图里：

```text
东京
大阪
京都
```

节点通常可以带属性：

```json
{
  "id": "Image_2",
  "type": "image",
  "page": 4,
  "caption": "系统架构图"
}
```

---

### 2. 边 Edge

**边**表示节点之间的关系或连接。

例如：

```text
小明 —— 认识 —— 小红
东京 —— 有路线到 —— 大阪
文本块 13 —— 解释 —— 图 2
```

边也可以带属性：

```json
{
  "source": "TextChunk_13",
  "target": "Image_2",
  "relation": "explains",
  "confidence": 0.87
}
```

---

### 3. 有向图 Directed Graph

如果边有方向，就是**有向图**。

```text
A → B
```

表示关系从 A 指向 B。

例如：

```text
文本块 13 → 解释 → 图 2
Apple → founded_by → Steve Jobs
用户问题 → 检索到 → 文档片段
```

方向很重要，因为：

```text
A → B
```

不一定等于：

```text
B → A
```

比如：

```text
Steve Jobs 创立 Apple
```

和：

```text
Apple 创立 Steve Jobs
```

意思完全不同。

知识图谱大多数是有向图。

---

### 4. 无向图 Undirected Graph

如果边没有方向，就是**无向图**。

```text
A —— B
```

表示 A 和 B 只是相互连接。

例如社交关系：

```text
小明 —— 是朋友 —— 小红
```

通常可以双向理解。

地图上的道路如果双向通行，也可以看作无向边：

```text
东京 —— 大阪
```

---

### 5. 加权图 Weighted Graph

如果边上有权重，就是**加权图**。

```text
A —— 0.8 —— B
```

权重可以表示：

```text
距离
成本
相似度
置信度
强弱关系
重要程度
```

例如：

```text
TextChunk_13 —— 0.91 explains —— Image_2
Image_2 —— 0.72 near —— TextChunk_14
东京 —— 515km —— 大阪
```

在多模态 RAG 里，权重很常见：

```text
文本块和图片的关系置信度
两个实体的语义相似度
图扩展时的路径分数
```

---

### 6. 度 Degree

**度**表示一个节点连接了多少条边。

例如：

```text
A —— B
A —— C
A —— D
```

A 的度是 3。

在有向图里，度又分为：

```text
入度 in-degree：有多少边指向它
出度 out-degree：它指向多少个节点
```

例如：

```text
A → B
C → B
B → D
```

B 的：

```text
入度 = 2
出度 = 1
```

在知识图谱中，度很高的节点通常是中心节点，比如：

```text
RAG
Transformer
某个核心章节
某个被多处引用的图表
```

---

### 7. 路径 Path

**路径**是从一个节点走到另一个节点经过的一系列边。

例如：

```text
A → B → C → D
```

这是一条从 A 到 D 的路径。

在知识图谱里：

```text
问题命中 TextChunk_13
TextChunk_13 references Image_2
Image_2 located_in Page_4
Page_4 belongs_to Section_2
```

路径就是：

```text
TextChunk_13 → Image_2 → Page_4 → Section_2
```

路径很重要，因为它支持多跳检索和多跳推理。

---

### 8. 跳数 Hop

**跳数**就是路径经过了几条边。

```text
A → B
```

是 1 跳。

```text
A → B → C
```

是 2 跳。

```text
A → B → C → D
```

是 3 跳。

在 RAG 的图检索里，经常会说：

```text
从命中的节点开始，扩展 1-hop 邻居
从命中的实体开始，扩展 2-hop 子图
```

比如：

```text
TextChunk_13
  1-hop → Image_2
  2-hop → Page_4
  3-hop → Section_2
```

跳数越多，召回越广，但噪声也越多。

---

### 9. 邻居 Neighbor

和某个节点直接相连的节点，就是它的**邻居**。

例如：

```text
A —— B
A —— C
A —— D
```

B、C、D 都是 A 的邻居。

在检索时经常会做：

```text
找到相关节点
→ 取它的邻居
→ 再取邻居的邻居
```

这叫**邻域扩展**。

---

### 10. 子图 Subgraph

**子图**是原图的一部分。

比如原图是：

```text
A —— B —— C
|     |
D —— E
```

其中：

```text
A —— B
|     |
D —— E
```

可以看作一个子图。

在知识图谱检索中，我们通常不会把整个图都交给大模型，而是抽出一个相关子图：

```text
用户问题
→ 命中几个实体
→ 扩展 1~2 跳邻居
→ 得到相关子图
→ 转成上下文给 LLM
```

例如：

```text
TextChunk_13
Image_2
Caption_2
Page_4
Section_2
Table_1
```

这就是一个和问题相关的局部子图。

---

### 11. 连通性 Connectivity

如果两个节点之间能通过路径到达，就说它们是**连通的**。

```text
A —— B —— C
```

A 和 C 是连通的。

如果是：

```text
A —— B     C —— D
```

那么 A/B 和 C/D 分别属于两个连通分量。

在知识图谱中，如果图被切得太碎，很多节点互相不连通，图检索效果会差，因为没法沿关系扩展。

---

### 12. 环 Cycle

如果从一个节点出发，沿着边走，最后又回到自己，就形成一个**环**。

```text
A → B → C → A
```

在一些图算法里，环会影响遍历，需要避免无限循环。

在知识图谱检索里，常见策略是：

```text
记录已经访问过的节点
限制最大跳数
限制最大候选数量
```

---

### 13. 稀疏图和稠密图

**稀疏图**：边比较少。

```text
A —— B —— C —— D
```

**稠密图**：边很多，节点之间连接密集。

```text
A —— B
|\  /|
| \/ |
| /\ |
|/  \|
C —— D
```

多模态 RAG 里的图通常不能太稀疏，也不能太稠密。

太稀疏：

```text
文本、图片、表格之间连不起来
```

太稠密：

```text
什么都互相关联，检索噪声很大
```

所以一般会给边加置信度、类型和权重。

---

### 14. 图的表示方式

图通常有两种基础表示。

#### 邻接表 Adjacency List

记录每个节点连接了谁。

```json
{
  "A": ["B", "C"],
  "B": ["A", "D"],
  "C": ["A"],
  "D": ["B"]
}
```

优点是节省空间，适合大图。

#### 邻接矩阵 Adjacency Matrix

用矩阵表示节点之间是否连接。

```text
    A B C D
A   0 1 1 0
B   1 0 0 1
C   1 0 0 0
D   0 1 0 0
```

如果 A 和 B 有边，矩阵里就是 1；没有边就是 0。

优点是查询两个节点是否相连很快，但大图会占用很多空间。

### 15. 图遍历

图遍历就是从一个节点出发，访问相关节点。

常见有两种。

#### BFS：广度优先搜索

一层一层扩展：

```text
先看 1-hop
再看 2-hop
再看 3-hop
```

适合做邻域扩展。

在 RAG 中：

```text
命中实体
→ 扩展一跳邻居
→ 再扩展二跳邻居
```

通常就是 BFS 思路。

#### DFS：深度优先搜索

沿着一条路一直走到底，再回头。

```text
A → B → C → D
```

适合路径搜索、结构探索，但在 RAG 检索里要小心跑太深。

---

### 16. 中心性 Centrality

中心性用于衡量一个节点在图里有多重要。

常见指标：

```text
度中心性：连接越多越重要
PageRank：被重要节点指向越多越重要
介数中心性：经常出现在路径中间的节点更重要
```

在多模态 RAG 里，可以用中心性辅助排序：

```text
被很多文本引用的图片更重要
连接多个章节的概念更重要
被多个表格支持的结论更重要
```

### 17. 图数据库里的 Label 和 Property

以 Neo4j 为例，一个节点可以有 label：

```text
(:Image)
(:TextChunk)
(:Page)
(:Entity)
```

节点可以有属性：

```text
id
title
page
content
summary
bbox
```

边也可以有类型和属性：

```text
(:TextChunk)-[:REFERENCES {confidence: 0.95}]->(:Image)
```

这比普通三元组更适合工程实现。

### 18. 放到多模态 RAG 里的例子

假设一个文档里有：

```text
第 4 页
一段正文
一张图
一个表格
```

可以建成图：

```text
Document_1
  → contains → Page_4

Page_4
  → contains → TextChunk_13
  → contains → Image_2
  → contains → Table_1

TextChunk_13
  → references → Image_2
  → explains → Image_2

Image_2
  → has_caption → Caption_2
  → located_in → Page_4

Table_1
  → supports → TextChunk_13
  → located_in → Page_4
```

用户问：

```text
“这段结论有什么图表支持？”
```

图检索可以走：

```text
TextChunk_13
  → references Image_2
  → supported_by Table_1
```

然后把 Image_2 和 Table_1 一起拿出来。

### 19. 你现在最该掌握的图概念

先重点理解这些就够：

```text
节点：对象
边：对象之间的关系
有向图：关系有方向
加权图：关系有强弱
度：节点连接数量
路径：节点之间怎么走
跳数：路径长度
邻居：直接相连的节点
子图：相关的一小块图
BFS：一层层扩展邻居
中心性：节点重要程度
```

对应到多模态 RAG：

```text
节点 = 文本块、图片、表格、章节、实体
边 = contains、located_in、references、explains、supports
路径 = 从问题命中的文本走到相关图片/表格
跳数 = 扩展几层关系
子图 = 本次回答需要的相关证据集合
```

一句话总结：

**图就是用节点表示对象，用边表示关系；图检索就是从相关节点出发，沿着边找到相关的一片子图。**
在多模态 RAG 里，图的作用就是让文本、图片、表格、公式这些内容不再孤立，而是能通过关系被一起召回。
