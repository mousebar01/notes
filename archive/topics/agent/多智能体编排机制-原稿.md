这块的核心不是自己手写一个 `StateGraph` 编排器，而是基于 **LangChain `create_agent` + middleware + 子智能体 task 工具** 来做多智能体编排。

## 入口：主 Agent 构图时挂载中间件

主 Agent 是 `ChatbotAgent`，在 `get_graph()` 里先做 runtime context 归一化，然后用 `create_agent(...)` 创建 LangGraph agent。关键点是 `middleware=await _build_middlewares(context)`，也就是多智能体能力被作为中间件插进去。

```python
graph = create_agent(
    model=load_chat_model(...),
    tools=await resolve_configured_runtime_tools(context),
    system_prompt=build_prompt_with_context(context),
    middleware=await _build_middlewares(context),
    state_schema=ChatBotState,
    checkpointer=await self._get_checkpointer(),
)
```

`_build_middlewares()` 里先挂文件系统、附件、Skills，然后调用：

```python
subagent_middleware = await create_subagent_task_middleware(context)
if subagent_middleware:
    middlewares.append(subagent_middleware)
```

也就是说：**只有当前主 Agent 配置了可见子智能体时，才会挂载子智能体调度能力**。

## 配置层：主 Agent 的 `subagents` 字段决定可调用范围

`ChatBotContext` 里专门加了一个 `subagents` 字段，类型是 `list[str] | None`。描述写得很明确：为空表示启用当前用户可见的全部子智能体。

```python
class ChatBotContext(BaseContext):
    subagents: list[str] | None = field(
        default=None,
        metadata={
            "name": "子智能体",
            "description": "可选子智能体列表，为空表示启用当前用户可见的全部子智能体。",
            "kind": "subagents",
        },
    )
```

更底层的 context 归一化会把 `subagents` 当作一种资源类型处理。它会从数据库里加载当前用户可见的子智能体，并只保留允许的 key。

## 数据模型：子智能体本质上也是 Agent

Yuxi 没有单独做一张 SubAgent 表。文档里说得很清楚：子智能体仍然是 `agents` 表中的一级 Agent，只是带 `is_subagent=true`，并使用专用后端 `SubAgentBackend`。

仓库代码里也定义了：

```python
DEFAULT_AGENT_BACKEND_ID = "ChatbotAgent"
SUB_AGENT_BACKEND_ID = "SubAgentBackend"
```

并且校验 `SubAgentBackend` 必须和 `is_subagent=True` 保持一致。

内置子智能体包括：

| slug                | 作用             |
| ------------------- | -------------- |
| `general-purpose`   | 通用任务处理         |
| `web-search`        | 网页检索           |
| `research-explorer` | 调研探索           |
| `fact-verifier`     | 事实核查           |
| `deep-research`     | 主编排型深度研究 Agent |

其中 `deep-research` 不是子智能体，而是普通主 Agent；它的配置里指定了 `subagents: ["research-explorer", "fact-verifier"]`，并绑定 `deep-research` skill。

## 编排方式：通过 `task` 工具派发子任务

真正的多智能体调用在 `backend/package/yuxi/agents/middlewares/subagent_task.py`。

它定义了一个 `YuxiSubAgentMiddleware`，初始化时会把可用子智能体整理成：

```python
self.subagents = {agent.slug: agent for agent in subagents}
self.system_prompt = TASK_SYSTEM_PROMPT.format(available_agents=available_agents)
self.tools = [self._build_task_tool(available_agents)]
```

也就是说它做两件事：
一是把“可用子智能体列表 + 使用规则”注入系统提示词；二是给主 Agent 暴露一个 `task` 工具。

`task` 工具有三个参数：

```python
description: str
subagent_type: str
thread_id: str | None = None
```

`description` 是子任务说明，`subagent_type` 是要调用的子智能体 slug，`thread_id` 用来继续之前的子智能体线程。这个和文档里的运行时调用链一致。

## 执行流程：父线程派生 child thread

一次 `task` 调用大概是这样走的：

1. 校验 `subagent_type` 是否在允许列表里。
2. 从父 Agent context 取 `parent_thread_id`、`file_thread_id`、`uid`。
3. 通过 `agent.backend_id` 找到真实后端，要求必须是 `SubAgentBackend`。
4. 如果没有传入 `thread_id`，就生成一个 child thread id；如果传了，就视为续跑。
5. 创建一条 `agent_runs` 记录，`run_type="subagent"`，并把 `parent_agent_run_id` 关联到父运行。
6. 构造子智能体 context。
7. 调用子智能体自己的 `backend.get_graph(context=child_context)`。
8. 用 `graph.ainvoke(...)` 执行子任务。
9. 把最终 assistant 文本和子智能体线程 ID 包装成 `ToolMessage` 返回给主 Agent。

这些步骤在代码里基本是直写的：校验、创建 run、构造 child context、调用 graph、完成/失败状态更新。

关键调用是：

```python
graph = await backend.get_graph(context=child_context)
result = await graph.ainvoke(
    _state_for_child(...),
    config=_child_config(...),
    context=child_context,
)
```

这说明子智能体不是伪工具、不是 HTTP 调用，而是直接启动另一个 Agent graph。

## 流式事件：把子智能体事件路由回前端

`BaseAgent` 里对 `astream_events(..., version="v3")` 做了封装。它会并行收集子智能体 routes，把 namespace、thread_id、subagent_type、tool_call_id 等信息补进事件 metadata。这样前端能知道某条消息/工具事件来自主 Agent 还是某个子 Agent。

相关辅助函数会从 `run.yuxi_subagents` 或 `run.subagents` 里收集子智能体路径，并记录：

```python
{
  "thread_id": thread_id,
  "parent_thread_id": parent_thread_id,
  "subagent_type": subagent_type,
  "tool_call_id": tool_call_id,
}
```

## 防止无限嵌套

文档里明确说：`SubAgentBackend` 不会挂载 `task middleware`，子智能体的 `subagents` 字段隐藏且默认为空，所以不会形成“子智能体再调用子智能体”的嵌套链路。

中间件文档也强调：子智能体自身不会再挂载下一层 `task` 中间件，避免形成嵌套子智能体链路。

## 总结成一句话

Yuxi 的多智能体编排是：

**主 Agent = LangGraph/LangChain `create_agent`；子智能体 = 数据库里的普通 Agent 配置；编排 = 主 Agent 通过 `YuxiSubAgentMiddleware` 获得 `task` 工具，把任务派发给指定 `SubAgentBackend` graph；每个子任务有独立 child thread、checkpoint、run 记录，但共享父会话的 uploads/outputs。**

这种设计的优点是：子智能体可以像普通 Agent 一样配置模型、工具、知识库、MCP、Skills；主 Agent 只需要通过 `task(description, subagent_type, thread_id?)` 来调度。


能。这个项目里的主 Agent 本身就是聊天 Agent。

在 Yuxi 里，主 Agent 是 `ChatbotAgent`，它的描述是“基础的对话机器人，可以回答问题，可在配置中启用需要的工具”，并且通过 `create_agent(...)` 创建 LangGraph/LangChain Agent graph。也就是说，**聊天能力不是子智能体提供的，而是主 Agent 的基础能力；多智能体只是它的一种扩展工具能力**。

## 主 Agent 怎么实现聊天

典型流程是：

```text
前端聊天输入
  ↓
后端 conversation / run 接口
  ↓
ChatbotAgent.get_graph()
  ↓
LangChain create_agent(...)
  ↓
LLM + tools + middleware + checkpointer
  ↓
流式返回消息 / 工具事件 / 状态
```

在代码上，`BaseAgent` 提供了通用的聊天入口，比如：

```python
stream_messages(messages, input_context)
invoke_messages(messages, input_context)
stream_messages_with_state(messages, input_context)
```

其中 `stream_messages()` 会把用户消息放进 graph，然后调用：

```python
graph.astream(
    {"messages": messages},
    stream_mode="messages",
    context=context,
    config=input_config,
)
```

所以它天然支持流式聊天。`configurable` 里会带 `thread_id` 和 `uid`，用来恢复同一个会话线程。

`invoke_messages()` 则是非流式调用：

```python
msg = await graph.ainvoke(
    {"messages": messages},
    context=context,
    config=input_config,
)
```

## 对话记忆怎么做

这个项目使用 LangGraph checkpointer 保存状态。`BaseAgent.get_graph()` 的抽象方法里明确要求编译 graph 时设置 checkpointer，否则无法获取历史记录。实际 `ChatbotAgent` 里传入的是：

```python
checkpointer=await self._get_checkpointer()
```

`_get_checkpointer()` 支持三种路径：

```text
优先：Postgres checkpointer
回退：SQLite checkpointer
再回退：内存 InMemorySaver
```

它默认看环境变量 `LANGGRAPH_CHECKPOINTER_BACKEND`，如果是 `postgres` 就用 Postgres，否则用 SQLite；SQLite 失败才用内存。

所以聊天历史不是靠前端拼接，而是通过：

```python
config = {"configurable": {"thread_id": thread_id, "uid": uid}}
state = await app.aget_state(config)
messages = state.values.get("messages", [])
```

从 LangGraph state 里取回。

## 多 Agent 聊天一般怎么做

常见有三种模式。

### 1. 主 Agent 聊天，子 Agent 做工具

这是 Yuxi 当前采用的模式。

用户只和主 Agent 对话。主 Agent 负责理解用户意图、拆任务、调用工具、调用子智能体、汇总结果。子 Agent 不直接面向用户，而是作为 `task` 工具被调用。

```text
User
 ↓
Main Chat Agent
 ├─ 普通工具：搜索、文件、知识库、MCP
 ├─ 子 Agent A：调研
 ├─ 子 Agent B：核查
 └─ 子 Agent C：写作/整理
 ↓
Main Agent 汇总后回复用户
```

优点是体验简单，用户只看到一个聊天对象；多智能体复杂性被封装在后端。Yuxi 的 `YuxiSubAgentMiddleware` 就是这个模式：给主 Agent 注入 `task` 工具，模型决定何时派发子任务。

### 2. 多 Agent 轮流发言

这种更像群聊或会议室。每个 Agent 都可能直接生成一条消息，例如：

```text
用户：帮我分析这个市场
Planner：我先拆成行业、竞品、风险三块
Researcher：我查到这些资料……
Critic：这里证据不足……
Writer：最终报告如下……
```

实现上通常需要一个 **orchestrator / supervisor** 决定下一个发言者是谁。可以用 LangGraph 写成状态机：

```text
START
 ↓
router
 ├─ planner
 ├─ researcher
 ├─ critic
 ├─ writer
 └─ END
```

每个节点读取共享 state 里的 messages，然后追加自己的消息。适合展示多角色协作过程，但用户体验更复杂，容易啰嗦。

### 3. Supervisor + specialist agents

这是企业应用里很常见的折中模式。

Supervisor 是唯一和用户聊天的 Agent；specialists 可以被调用，但它们的中间过程可以选择展示或隐藏。

```text
User ↔ Supervisor
          ├─ Data Analyst
          ├─ Knowledge Retriever
          ├─ Compliance Reviewer
          └─ Report Writer
```

Yuxi 的设计更接近这个模式，只是 specialists 被实现为 `task` 工具背后的真实 Agent graph。

## 聊天功能最小实现需要什么

一个多 Agent 聊天系统通常至少要有这些组件：

```text
1. Conversation / Thread
   保存一次对话的 thread_id

2. Message State
   保存 Human / AI / Tool messages

3. Main Agent
   负责直接面向用户

4. Tool Calling
   让主 Agent 能调用搜索、知识库、文件、子 Agent

5. Memory / Checkpointer
   恢复历史上下文

6. Streaming
   把 token、工具状态、子任务状态推给前端

7. Run records
   记录每次执行状态：running / completed / failed / cancelled
```

Yuxi 基本都有这些：`thread_id`、`uid`、LangGraph state、checkpointer、`astream_events`、`agent_runs`、`subagent_runs`、middleware 链路。

## 一个简化伪代码

如果自己实现，结构可以像这样：

```python
async def chat(user_message, thread_id, uid):
    context = ChatContext(
        thread_id=thread_id,
        uid=uid,
        subagents=["researcher", "critic"],
    )

    graph = create_agent(
        model=llm,
        tools=[
            search_tool,
            knowledge_tool,
            task_tool,  # 调用子智能体
        ],
        system_prompt="你是主聊天助手，必要时委派子任务。",
        middleware=[
            subagent_middleware,
            summary_middleware,
            token_usage_middleware,
        ],
        checkpointer=postgres_checkpointer,
    )

    async for event in graph.astream_events(
        {"messages": [{"role": "user", "content": user_message}]},
        config={"configurable": {"thread_id": thread_id, "uid": uid}},
    ):
        yield event
```

子智能体调用大概是：

```python
async def task(description, subagent_type, thread_id=None):
    child_thread_id = thread_id or make_child_thread_id()

    subagent = load_agent(subagent_type)
    child_graph = await subagent.get_graph(
        context=SubAgentContext(thread_id=child_thread_id)
    )

    result = await child_graph.ainvoke({
        "messages": [{"role": "user", "content": description}]
    })

    return {
        "thread_id": child_thread_id,
        "result": result["messages"][-1].content,
    }
```

## 关键设计取舍

我建议一般产品优先采用 **“主 Agent 聊天 + 子 Agent 工具化”** 的方式，也就是 Yuxi 现在这种。

原因是它最符合聊天产品直觉：用户只需要和一个助手说话；主 Agent 决定是否调用子 Agent；子 Agent 的结果被汇总成最终回答。需要透明度时，再把子 Agent run 状态、工具调用、引用来源展示在侧边栏或过程面板里，而不是把所有 Agent 的中间发言都塞进主对话流。


有区别。简单说：

```text
LangChain = 组件库 / Agent API / 工具生态
LangGraph = 状态机 / 编排运行时 / 持久化对话图
```

在 Yuxi 里，两者是一起用的：**用 LangChain 的 `create_agent` 创建 Agent，用 LangGraph 作为底层 graph 运行、stream、checkpoint 和 state 管理。**

## 1. LangChain 是什么

LangChain 更偏“应用层组件库”。它主要提供：

```text
LLM 封装
Prompt / Message 抽象
Tool calling
Agent 创建接口
Middleware
Retriever / RAG 组件
模型适配器
```

比如 Yuxi 里主 Agent 使用的是：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import ModelRetryMiddleware, TodoListMiddleware
```

也就是说，**Agent 怎么创建、工具怎么挂、中间件怎么加**，这部分主要是 LangChain 提供的。

可以把 LangChain 理解成：

```text
“我想快速搭一个能调用工具的 LLM Agent”
```

## 2. LangGraph 是什么

LangGraph 更偏“运行时和状态编排”。它解决的是：

```text
状态如何保存
节点如何流转
多步骤任务如何恢复
对话历史如何 checkpoint
工具调用事件如何 stream
复杂 agent workflow 如何编排
多 agent 如何做 supervisor / router / worker
```

Yuxi 的 `BaseAgent` 里就直接依赖 LangGraph 的能力：

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver
from langgraph.graph.state import CompiledStateGraph
from langgraph.types import Command
```

`BaseAgent.get_graph()` 返回的也是：

```python
CompiledStateGraph
```

这说明最终跑起来的是 LangGraph 编译后的状态图。

可以把 LangGraph 理解成：

```text
“我想让 Agent 像一个可恢复、可观测、可分支的状态机一样运行”
```

## 3. 两者关系

现在 LangChain 的新 Agent 系统底层很多能力就是基于 LangGraph 的。

所以你在代码里看到：

```python
graph = create_agent(...)
```

虽然调用来自 `langchain.agents`，但返回出来的其实是一个可运行的 graph，能执行：

```python
graph.ainvoke(...)
graph.astream(...)
graph.astream_events(...)
graph.aget_state(...)
```

这些更像 LangGraph 的运行时能力。

可以这样理解：

```text
LangChain create_agent
  ↓
帮你组装一个标准 ReAct / tool-calling Agent
  ↓
底层产物是 LangGraph graph
  ↓
通过 LangGraph 做状态、流式、checkpoint、恢复
```

## 4. 在 Yuxi 中各自负责什么

| 能力           | LangChain          | LangGraph                    |
| ------------ | ------------------ | ---------------------------- |
| 创建 Agent     | ✅ `create_agent`   | 底层承载                         |
| 模型调用         | ✅                  | 间接参与                         |
| 工具抽象         | ✅ `StructuredTool` | 工具节点运行                       |
| Middleware   | ✅                  | 与 graph 执行链结合                |
| 对话状态         | 部分                 | ✅                            |
| checkpoint   | 不是重点               | ✅ SQLite / Postgres / Memory |
| 流式事件         | 部分                 | ✅ `astream_events`           |
| 子 Agent 返回状态 | 部分                 | ✅ `Command(update=...)`      |
| 自定义状态图       | 不适合复杂图             | ✅                            |
| 多 Agent 编排   | 可用 Agent/tool      | ✅ 更适合复杂拓扑                    |

## 5. 用一个比喻

```text
LangChain 像“零件和标准机器人套件”
LangGraph 像“机器人运行时和流程控制系统”
```

LangChain 给你：

```text
模型、工具、Agent、middleware、prompt 接口
```

LangGraph 给你：

```text
状态图、节点流转、checkpoint、恢复、事件流、并发控制
```

## 6. 为什么 Yuxi 两个都用

因为 Yuxi 的需求既要快速构建 Agent，又要支持复杂运行时：

```text
普通聊天
工具调用
文件系统 middleware
Skills middleware
子智能体 task middleware
长上下文 summary
流式返回
历史恢复
子 Agent child thread
agent_runs 状态记录
```

如果只用 LangChain，Agent 能跑，但状态恢复、复杂事件流、checkpoint 管理会弱很多。

如果只用 LangGraph，需要自己手写很多 agent/tool 调用逻辑，开发成本更高。

所以 Yuxi 采用的是：

```text
LangChain 负责“Agent 组装”
LangGraph 负责“Agent 运行”
```

## 7. 什么时候只用 LangChain，什么时候用 LangGraph

只用 LangChain 适合：

```text
简单聊天机器人
一次性工具调用
简单 RAG 问答
不太需要复杂状态恢复
不需要多节点流程
```

用 LangGraph 适合：

```text
多轮复杂任务
多 Agent 编排
需要 checkpoint / resume
需要人工确认节点
需要循环、分支、条件路由
需要可观测事件流
需要严格控制执行流程
```

如果你要做 Yuxi 这种系统，我会选：

```text
LangChain create_agent 起步
LangGraph 管状态和编排
复杂逻辑再手写 StateGraph
```

## 8. 放到多 Agent 场景里

多 Agent 有两种实现方式：

### A. LangChain Agent + task 工具

Yuxi 当前就是这个思路：

```text
主 Agent 是一个 LangChain create_agent
子 Agent 被包装成 task 工具
底层用 LangGraph thread/checkpoint 管理状态
```

优点是实现简单，适合“主 Agent 调度专家 Agent”。

### B. 直接用 LangGraph StateGraph

如果你要更强控制，比如固定流程：

```text
planner → researcher → verifier → writer → reviewer
```

就可以直接用 LangGraph 写：

```python
workflow = StateGraph(MyState)

workflow.add_node("planner", planner_node)
workflow.add_node("researcher", researcher_node)
workflow.add_node("verifier", verifier_node)
workflow.add_node("writer", writer_node)

workflow.add_conditional_edges("planner", route_next)
workflow.add_edge("researcher", "verifier")
workflow.add_edge("verifier", "writer")

graph = workflow.compile(checkpointer=checkpointer)
```

这种更适合流程确定、需要强控制的多 Agent 系统。

## 结论

在这个项目里：

```text
LangChain = 帮你快速创建会聊天、会调用工具、会挂 middleware 的 Agent
LangGraph = 让这个 Agent 变成可持久化、可流式、可恢复、可编排的状态图
```

Yuxi 的实现选择比较务实：**主 Agent 和子 Agent 都用 LangChain `create_agent` 生成，底层依赖 LangGraph 管 state、thread、checkpoint、stream 和子任务返回。**
