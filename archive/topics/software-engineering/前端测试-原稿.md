# 前端测试

这篇记录前端测试的分层思路：用单元测试、组件测试和少量 E2E 测试分别覆盖不同风险，而不是把所有问题都丢给 Playwright。

## 核心思路

现在这套前端测试的核心思路是：**按测试金字塔分层，不把所有问题都丢给 Playwright。**

底层用 **Vitest 单元测试**，主要测前端自己的纯逻辑：配置映射、搜索匹配、分页规则、参数拼装、错误文案格式化。这类测试跑得快、失败原因清楚，最适合防止 AI 改代码时把业务规则顺手改坏。

中层用 **React Testing Library 组件集成测试**，主要测“后端数据进入组件以后，用户看到什么、点击后触发什么”。重点不是测 AntD 组件内部是否正常，而是测我们自己的页面约束，比如设置页不要显示路径噪声、点击配置项不要误跳转、公开供应商可见而本地供应商隐藏。

顶层用 **Playwright 冒烟测试**，只测很少的关键路径：应用能打开、主导航能进设置页、基础交互不会崩、关键页面状态没有明显跑偏。E2E 很有价值，但维护成本高，所以不能拿它替代单元测试和组件测试。

组织经验上，我现在用的是混合结构：

```text
src/xxx/foo.ts
src/xxx/foo.test.ts

src/xxx/View.tsx
src/xxx/View.test.tsx

tests/e2e/*.spec.ts
```

也就是：**单元/组件测试放源码旁边，E2E 单独放目录**。这样改功能时能顺手看到对应测试，而跨页面流程又不会散落在各个模块里。

还有几个经验点：

- 不测 AntD 内部行为，只测我们传给它的数据和用户侧结果。
- 不用大快照锁 DOM，太脆，改 UI 会烦死。
- E2E 要 mock 后端，避免依赖本机数据、Cookie、真实服务状态。
- 测试应该保护“产品约束”，不是保护“当前实现细节”。
- AI 容易写坏的是映射、过滤、状态派生、点击后副作用，这些最值得测。
- 每一层测试都要有明确职责：单测快而细，组件测交互语义，E2E 测整体能不能跑通。

一句话总结：**前端测试不是越像用户越好，而是越能用最低成本锁住真实风险越好。**

## E2E 是什么

E2E 是 **End-to-End Testing，端到端测试**。

它的意思是：**从用户视角，把整个应用像真实用户一样跑一遍，验证完整流程是否正常。**

比如一个登录流程：

```text
打开登录页
→ 输入账号密码
→ 点击登录按钮
→ 跳转到首页
→ 看到用户名
```

这就是 E2E 测试。

和组件测试的区别大概是：

| 类型     | 测试对象            | 例子                           |
| ------ | --------------- | ---------------------------- |
| 单元测试   | 一个函数、一个小模块      | `formatDate()` 输入日期，输出格式是否正确 |
| 组件测试   | 一个 React/Vue 组件 | Button 点击后是否触发 `onClick`     |
| E2E 测试 | 整个用户流程          | 用户能不能登录、下单、提交表单、上传文件         |

E2E 一般会启动真实浏览器，比如 Chrome，然后用工具自动操作页面：

```ts
test('user can login', async ({ page }) => {
  await page.goto('http://localhost:3000/login');

  await page.getByLabel('Email').fill('test@example.com');
  await page.getByLabel('Password').fill('123456');
  await page.getByRole('button', { name: 'Login' }).click();

  await expect(page.getByText('Welcome')).toBeVisible();
});
```

常见 E2E 工具有：

| 工具         | 说明                                    |
| ---------- | ------------------------------------- |
| Playwright | 现在很常用，支持 Chrome、Firefox、Safari/WebKit |
| Cypress    | 前端圈很流行，调试体验好                          |
| Puppeteer  | 偏底层，常用于 Chrome 自动化                    |
| Selenium   | 老牌方案，企业里仍然很多                          |

E2E 能测到组件测试测不到的东西，比如：

```text
页面真的能打开吗？
路由跳转正常吗？
接口联调正常吗？
登录态正常吗？
弹窗会不会被遮挡？
按钮在真实浏览器里能不能点？
表单提交后数据有没有保存？
```

但 E2E 也有缺点：**慢、容易受环境影响、维护成本高**。所以实际项目里通常是：

```text
大量单元/组件测试
+ 少量关键 E2E 测试
+ 必要的视觉回归测试
```

你可以这样理解：

**组件测试是在问：“这个零件本身好不好？”
E2E 测试是在问：“用户从头到尾真的能不能完成任务？”**
