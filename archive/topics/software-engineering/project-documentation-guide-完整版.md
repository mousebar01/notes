# 项目文档编写指南：让读者能够解释、修改和排障系统

项目文档的目标不是证明作者读过代码，而是把理解系统所需的推理交给下一位读者。读者看完后，应该能够回答以下问题：

- 这个系统解决什么问题，最重要的对象和边界是什么？
- 一次真实操作如何穿过系统，状态在哪里发生变化？
- 为什么采用当前设计，约束和放弃的方案是什么？
- 哪些条件必须始终成立，失败后如何观察、恢复或重试？
- 如果要修改系统，应该尊重哪些边界，而不是先背下目录结构？

如果一份文档只能告诉读者“有什么类、函数和文件”，它至多是代码索引。高质量文档传递的是一套可以继续推理的模型。

本文基于 SQLite、Zulip、GitLab、Pro Git 和 Home Assistant 开发者文档的对比阅读，并结合 Vidraft 现有自动生成文档的实际问题，给出一套适合中小型工程项目的写作方法。

## 一、先给结论

优秀项目文档虽然体量和读者不同，但有一组稳定的共同点：

1. 先声明读者和阅读结果，再决定写什么。
2. 先建立少量、稳定的核心概念，再展开组件和细节。
3. 以请求、状态或数据的流动组织叙述，而不是以目录组织叙述。
4. 不只说明“系统怎样做”，还解释“为什么只能或更适合这样做”。
5. 把约束、不变量、失败和恢复视为主流程的一部分。
6. 用具体例子验证模型，而不是用例子代替模型。
7. 通过渐进展开控制细节，让总览、深入解释和参考信息各司其职。
8. 对页面数量保持克制。一个新名词不等于一个新页面，一个类也不等于一个 topic。
9. 把易变参数和稳定设计分开，降低文档失效速度。
10. 把代码、测试、配置和日志当作证据，不把文件路径当作正文骨架。

可以把这些原则压缩成一条因果链：

```text
读者问题
  -> 核心模型
  -> 真实流程
  -> 设计约束
  -> 当前选择
  -> 代价与不变量
  -> 失败和恢复
  -> 可验证的例子
```

这条链比“模块 A、模块 B、模块 C”更接近开发者实际理解和修改系统的过程。

## 二、研究样本与本地存放方式

### 为什么放在项目外

参考仓库统一放在：

```text
/home/sy/project/documentation-reference-repos/
```

这个位置比放进 Vidraft 仓库更合适，原因是：

- 它们是研究材料，不是 Vidraft 的构建依赖。
- 不会污染 Vidraft 的 Git 状态、搜索结果、镜像体积和代码统计。
- 可以独立执行浅克隆、稀疏检出、更新或整体删除。
- 后续研究其他项目时，可以复用同一个参考库目录。

本次保存的参考项目如下。仓库均使用浅克隆或稀疏检出；SQLite 另外保存了所研究的官网页面快照，因为 SQLite 官网文档与 GitHub 源码镜像并非同一套发布源。

## 三、优秀文档真正共同的地方

### 1. 开头先建立阅读契约

SQLite 的架构文章一开始就说明，它面向希望理解或修改 SQLite 内部实现的人。Zulip 的架构总览先限定讨论的是服务端和 Web 应用。GitLab 的组件细节明确面向系统管理员和支持工程师。Pro Git 则直接告诉读者，理解 Git 如何思考数据，会让后续使用更容易。

这种开头不是礼貌性的“本文介绍……”，而是在做三件事：

- 排除不属于本文的读者问题。
- 说明读完后应获得什么能力。
- 决定后续需要多少实现细节。

写作前可以先完成一句话：

> 本文帮助【哪类读者】在【什么情境】下回答【什么问题】或完成【什么任务】，不负责【哪些相邻问题】。

如果这句话写不清楚，页面边界通常也不会清楚。

### 2. 先给心智模型，再给名词清单

Pro Git 的经典标题是“Snapshots, Not Differences”。它不先介绍命令，而是先纠正读者对版本控制的默认理解：Git 把历史理解为一串文件系统快照，而不是在基础文件上累积的一组差异。随后，本地操作、完整历史、分支和对象存储都可以从这个模型继续推导。

Home Assistant 用 Event Bus、State Machine、Service Registry 和 Timer 四个对象概括 Core。SQLite 则用下面这条管线建立全局模型：

```text
SQL 文本
  -> Tokenizer
  -> Parser
  -> Code Generator
  -> Bytecode Virtual Machine
  -> B-Tree
  -> Pager
  -> OS Interface
```

好模型具备三个特征：

- 数量少，读者可以在短时记忆中保留。
- 关系明确，不只是并列名词。
- 能预测后续行为，而不只是给组件贴标签。

Vidraft 的文档也应先让读者记住“资源如何成为证据，证据如何进入一次 Agent 运行，结果如何被保存并回到对话界面”，再讨论任何实现细节。

### 3. 围绕流动和状态写，而不是围绕目录写

Zulip 的 Events System 不是从事件相关文件列表开始，而是从一个真实问题开始：多个客户端持有旧状态时，系统如何让它们保持一致？它随后把问题拆成 Generation、Delivery 和 UI updates，并沿一次事件的生命周期解释职责。

GitLab 不止列出 NGINX、Workhorse、Puma、Gitaly 和 PostgreSQL，还分别描述 Web HTTP 请求、Git over HTTP 和 Git over SSH 的路径。组件因此获得了上下文：读者知道它何时参与、接收什么、把什么交给谁。

适合用作叙述主线的“流”通常有：

- 一次用户请求。
- 一份数据从进入到可消费的生命周期。
- 一个后台任务的状态变化。
- 一个事件从产生到确认的过程。
- 一次失败从症状到恢复的过程。

目录树只能回答“东西放在哪里”，不能回答“系统为什么这样运转”。对初次理解架构的读者，后者更重要。

### 4. Why 必须由真实约束支撑

“为了扩展性”“为了可维护性”“这样更灵活”不是设计理由，它们只是没有证据的正面形容词。优秀文档会把理由落到可观察的约束上。

SQLite 特别说明 Tokenizer 调用 Parser，而不是常见的反方向，原因是这种安排更容易做到线程安全并且运行更快。Zulip 说明 Tornado 只负责长连接上的事件投递，不执行数据库和缓存查询，因为单线程异步服务器中的一次阻塞会延迟成千上万条连接，而当前 Django 数据库库也不支持那条异步路径。

GitLab 把部署现实写成架构规则：传统 Linux 安装中不同服务可以共享文件系统，但 Kubernetes 中不能假设这一点。因此新服务需要通过 API 交换信息，并优先考虑 Kubernetes 兼容性。

可信的 Why 通常来自以下来源：

- 性能、延迟或资源上限。
- 一致性、事务或幂等要求。
- 安全和租户隔离。
- 部署环境和故障模型。
- 外部协议或兼容性。
- 用户工作流和可恢复性。
- 团队维护成本和迁移成本。

如果代码和历史材料无法证明某个动机，应明确写“当前能确认的约束是……”，不要替过去的作者补造一个听起来合理的故事。

### 5. 主动回答“为什么不用另一个方案”

Zulip 的架构总览直接回答了一个常见问题：能否用 Redis 同时替换 memcached 和 RabbitMQ？文档没有以“技术选型如此”结束，而是逐项分析：主要内存消耗不会减少，各服务的最低开销很低，不同数据需要不同的驱逐和持久语义，最后很可能仍要运行多个 Redis 实例。

这类段落价值很高，因为它阻止后来的维护者重复同一轮探索。只有满足下面条件时才值得记录替代方案：

- 它是后来者很可能再次提出的方案。
- 它与当前方案之间存在真实取舍。
- 选择会影响边界、数据或长期维护。
- 已有足够证据说明当时为何没有采用。

不要为每一个微小实现决定编造三种“备选方案”。那会把文档写成形式化表演。

### 6. 把不变量、失败和恢复写进设计

SQLite 的 Atomic Commit 先声明硬件假设，再沿真实写入顺序解释提交。它把删除 rollback journal 定义为可观察的 commit point，并分别推导断电发生在它之前和之后会得到什么结果。文章没有在正常提交结束处停止，而是继续讨论回滚、优化、测试和 Things That Can Go Wrong。读者因此看到的不是“提交步骤”，而是一套建立在明确故障模型上的正确性论证。

Zulip 的事件文档说明，接收者范围过大会造成安全泄露，过小会造成客户端同步错误；事件必须在数据库事务提交后发送。它还用网络响应可能丢失解释 `last_event_id` 为什么存在，并用队列回收后的重新注册说明系统如何自愈。

更精彩的例子是初始状态加载。Zulip 需要同时得到“当前状态”和“之后发生的事件”，但几十个数据源无法放在一个原子事务里。它采用“先建事件队列、非原子抓取状态、补抓期间事件、把事件应用到状态”的算法，并明确指出代价是必须正确实现 `apply_events`。随后，文档给出自动化测试如何验证“旧状态加事件”与“变化后的新状态”等价。

这段内容同时回答了：

- 目标是什么。
- 为什么简单方案做不到。
- 当前算法怎样工作。
- 正确性依赖什么不变量。
- 代价落在哪里。
- 测试如何证明它。

这就是高质量 How/Why 文档应达到的因果密度。

### 7. 使用渐进展开，而不是一次倾倒全部细节

GitLab 先给简化组件图，再给包含端口和可选服务的详细图，最后才进入组件清单和请求周期。Pro Git 把日常操作放在前九章，把 plumbing commands 和对象数据库放在最后；读者可以先使用系统，再按需要理解内部原理。Home Assistant 的 Core 总览只有四个核心对象和一张图，具体集成规则另有深入材料。

渐进展开不是“每层都新建一个页面”。它的本质是按读者问题安排信息顺序：

1. 一句话模型。
2. 一张能走通的主流程图。
3. 关键职责、边界和不变量。
4. 复杂分支与失败场景。
5. 易变参数、完整协议和 API 参考。

对中小项目，前四层完全可以是一篇结构良好的文档。只有第五层或一个真正独立的读者任务，才常常需要单独页面。

### 8. 用实例证明模型，而不是堆砌实例

Pro Git 先解释 content-addressable filesystem，再用底层命令逐步创建 blob、tree、commit 和 ref。命令不是孤立教程，而是让读者亲手验证对象模型。

Home Assistant 的 Integration Quality Scale 使用固定结构：Reasoning、Example implementation、Exceptions。以“数据更新”规则为例，它不仅要求写轮询间隔，还解释用户为何需要知道它：五分钟轮询和主动推送会形成完全不同的使用预期。如果设备无法承受高频请求，限制也必须写明。

一个好例子应至少满足一项：

- 让抽象关系变得可观察。
- 暴露一个容易误解的边界。
- 展示正常路径和失败路径的差别。
- 让读者可以验证预期结果。

与设计无关的大段配置、响应或代码，只会制造阅读负担。

## 四、五个项目分别值得学什么，又不能照搬什么

### SQLite：一条主干解释完整系统

SQLite Architecture 最值得学的是收敛。文章先说“SQL 被编译为字节码，再由虚拟机运行”，然后沿编译与执行管线解释每个组件。图和正文使用同一组概念，读者不用在两套术语之间翻译。

这种写法在其他文章中仍然一致。Atomic Commit 围绕“如何制造提交原子性的外部效果”组织一篇完整长文；Query Planner 从头到尾复用同一个 `FruitsForSale` 数据集，逐层比较全表扫描、单列索引、多列索引和覆盖索引。例子持续成长，因此读者能看到每个新机制究竟解决了上一步的什么限制。Appropriate Uses 则同时写适用和不适用场景，避免把设计边界写成单向宣传。

适合借鉴：

- 先给一条端到端主干，再解释节点。
- 每个组件都说明输入、输出和责任。
- 对反直觉关系补充明确理由。
- 将核心、后端和辅助能力区分开。
- 用硬件假设、commit point、故障结果和测试闭合正确性论证。
- 让一个贯穿全文的例子逐步增加复杂度。

不宜照搬：

- 后半部分逐渐进入源文件和函数位置，这对修改 SQLite 内核有帮助，但不适合作为一般项目架构文档的主结构。
- Architecture 对历史替代方案和演进边界讲得较少，需要 Atomic Commit、测试材料或决策记录补足。
- 数据库核心机制足够稳定，值得使用很长的连续文章；普通项目的每个流程不需要复制同样篇幅。

### Zulip：把架构写成可继续推理的约束

Zulip 最强的地方不是组件介绍，而是它经常解释“在什么故障模型下，这个设计才成立”。事件、缓存和队列文章都把正确性风险、部署影响和测试策略连接起来。

适合借鉴：

- 在组件职责后紧跟“它明确不做什么”和原因。
- 回答维护者最可能提出的替代方案。
- 从安全泄露、竞态、缓存污染等失败方式倒推不变量。
- 将测试写成设计正确性的证明方法，而不是单独的测试命令列表。

不宜照搬：

- Zulip 规模大、贡献者多，Subsystems 页面很多。Vidraft 不需要为每个子系统复制同样的页面粒度。
- 部分总览仍包含大量路径和部署细节，阅读主线会被实现定位信息打断。

### GitLab：用部署现实约束未来设计

GitLab 的架构文档能同时服务不同深度的读者：简化图用于建立方向，详细图用于排障，请求周期用于理解真实协作。它最有价值的一段不是组件表，而是从 Linux 与 Kubernetes 的差异推导“服务间不要依赖共享文件，新能力优先采用 API 边界”。

适合借鉴：

- 一张图只回答一个深度的问题。
- 用请求类型解释组件组合，而不是只写静态拓扑。
- 把部署约束写成未来设计的 guardrail。
- 区分核心处理组件、数据组件和监控组件。
- 把 Concept、Task、Reference、Troubleshooting 当作内容角色，允许在同一篇短文中组合。

不宜照搬：

- 完整组件表非常宽且很长，适合大型部署参考，不适合中小项目的架构入口。
- 同一页面混入系统布局、日志位置、配置文件和维护命令后，架构解释与运维参考的边界变弱。
- 大型组织的文档工作流和跨团队治理成本，不适合直接移植到 Vidraft。

### Pro Git：先改造读者的认知，再教操作

Pro Git 最值得学的是教学次序。它知道读者会带着其他版本控制系统的旧模型来学习，所以先用“差异”与“快照”的对比消除错误预期，再说明本地历史、完整性和三种状态。

适合借鉴：

- 识别读者最可能带来的错误模型。
- 用对比图和短句建立新的核心模型。
- 从结构事实推导能力，而不是列功能卖点。
- 让深入示例逐步验证前面的模型。

不宜照搬：

- 它是一整本书，允许较长铺垫和重复。项目内部文档应更快到达工作所需的模型。
- 教学叙事不能替代准确的接口、限制和运维参考。

### Home Assistant：把“文档要好”变成可检查规则

Home Assistant 用四个核心对象建立稳定词汇，又用 Integration Quality Scale 将文档要求落到具体规则：高层说明、支持能力、数据更新、已知限制、故障排查和使用场景。每条规则都解释 Reasoning，而不是只给格式要求。

适合借鉴：

- 为核心领域建立少量、一致的词汇。
- 每项规范同时写理由、示例和例外。
- 区分已知限制与临时 bug，避免和 issue tracker 重复。
- 故障排查按 Symptom、Description、Resolution 编写。

不宜照搬：

- 数十条规则各占一个页面，适合大型社区的审核和复用，但会让小项目严重碎片化。
- Core 总览非常短，缺少历史取舍和失败模型，不能单独承担完整架构解释。

## 五、页面不是知识的最小单位

### 四种写作模式不等于四套目录

项目文档通常包含四种写作模式：

| 模式 | 读者的问题 | 主要内容 |
| --- | --- | --- |
| 解释 | “为什么系统这样设计？” | 模型、边界、约束、不变量、取舍 |
| 操作指南 | “怎样完成一个具体任务？” | 前提、步骤、检查点、失败恢复 |
| 参考 | “精确契约是什么？” | API、配置、事件、字段、默认值 |
| 决策记录 | “为什么当时选择了这个方向？” | 背景、备选、决定、后果、重审条件 |

这四种模式需要在写作时区分，但不必机械地变成四个页面。对于同一读者、同一工作流、同一更新节奏的内容，使用同一篇文档中的清晰章节通常更好。

GitLab 的文档规范也采用这一判断：Concept、Task、Reference 和 Troubleshooting 是内容角色，短页面可以先解释概念，再紧接操作或参考；只有一两句话的 topic 应合并进现有内容。这比“每种类型一个目录、每个概念一个页面”更适合 Vidraft。

例如，一篇“Agent Runtime”文档可以先解释 Python 与 Pi 的责任边界，再描述一次运行的生命周期，最后附上事件参考和常见失败。只有当事件协议变得足够大、被多个读者独立查询时，才拆成单独参考页。

### 新建页面的五个门槛

只有当下面至少一个条件明确成立时，才建议创建新页面：

1. 它回答一个可独立进入、可独立完成的读者任务。
2. 它面向明显不同的读者，例如使用者与运行维护者。
3. 它与父文档具有不同的更新频率或责任人。
4. 它是会被多个地方重复查询的稳定参考契约。
5. 合并后主文档无法维持一条清楚的阅读主线。

反过来，如果一个标题自然地可以成为现有页面的二级章节，而且读者、问题和生命周期相同，就应该先合并。

不要使用固定字数作为拆页标准。篇幅只能提示问题，不能替代读者任务判断。

Zulip 的 Events System 超过 400 行，仍然是一篇连贯文档，因为它始终回答“多个客户端如何可靠地保持状态一致”。相反，一个只有几十行、仅描述单个模型类的页面即使很短，也未必值得独立存在。长短不是核心，问题是否完整才是核心。

### Vidraft 当前 Almanac 的碎片化信号

在本次研究快照中，`almanac/` 有 62 个 Markdown 页面，平均约 56 行，其中 54 个不足 60 行，只有 2 个达到 100 行。行数本身不能证明页面无价值，但这个分布与阅读体验共同说明：当前知识被切得比读者问题更细。

例如，Agent run lifecycle、Pi runtime、prompts and skills 实际服务同一类读者，并共同回答“一次 Vidraft Agent 运行怎样成立”。把它们作为一篇主文档的章节，读者更容易理解上下文、责任边界和因果关系。相反，部署、备份恢复、排查导入失败等操作任务可以保留独立入口，因为读者会在具体情境下单独寻找它们。

一个实用判断是：

> 拆页降低的是阅读负担，还是只把作者的分类成本转移给了读者？

## 六、适合 Vidraft 规模的文档集合

Vidraft 当前更适合约 10 到 11 份主要文档，而不是按模块和符号生成几十个 topic。下面是一套建议的信息架构；最终名称可以调整，但每篇都必须对应一个真实读者问题。

| 文档 | 主要回答的问题 | 应包含的内容 |
| --- | --- | --- |
| README | 这是什么，怎样最快跑起来？ | 产品定位、最短启动路径、文档导航 |
| 产品与领域模型 | 用户在管理什么，核心循环是什么？ | Workspace、Library、Resource、Evidence、Run 等稳定概念 |
| 系统架构 | 主要边界如何协作？ | 总体图、前后端边界、存储和外部运行时边界、关键不变量 |
| 资源与导入 | 文件如何成为可管理资源？ | 来源差异、共享导入流程、状态提交、失败与重试 |
| 检索与引用 | 原始内容如何成为可核验证据？ | 材料模型、召回阶段、范围约束、Citation 语义、限制 |
| Agent Runtime | 为什么使用 Pi，一次运行怎样完成？ | Python/Pi 边界、上下文与证据、事件、取消、持久化、失败 |
| 对话工作台 | 用户如何观察和控制一次运行？ | 对话状态、进度与结果、证据交互、刷新恢复、错误状态 |
| 后台工作与恢复 | 长任务如何推进并在失败后恢复？ | 状态机、幂等、诊断、重试、进程重启行为 |
| 开发与测试 | 怎样安全地修改和验证项目？ | 环境、常用任务、测试策略、跨边界修改检查点 |
| 部署与运维 | 系统怎样运行、升级、备份和排障？ | 部署模型、持久数据、配置、日志、备份恢复、故障排查 |
| 决策记录 | 哪些重要选择不应被反复重新讨论？ | 简短决策日志；仅为重大、长期决定建立独立 ADR |

以下内容通常不应再作为独立主文档：

- 单纯的项目目录树。
- 模块、依赖和 Provider 清单。
- 与开发指南分离的短测试说明。
- 每个路由、存储类、Prompt 或工具一个架构 topic。
- 只有三到十行、没有备选和后果的 ADR。

它们可以作为相关主文档中的参考章节，或者由代码、类型、配置 schema 和自动生成 API 参考直接承担。

## 七、从代码事实写出 How 和 Why

### 第一步：定义读者要做出的判断

不要从“我要介绍检索模块”开始。改为明确读者看完后要能做什么，例如：

- 判断一个新来源应该接入导入层还是检索层。
- 判断一项能力应由 Vidraft 后端还是 Pi runtime 拥有。
- 排查为什么回答完成了但引用没有出现。
- 判断一次后台任务能否安全重试。

这些判断会自然暴露文档必须讲清的模型、边界和不变量。

### 第二步：建立证据账本

在写正文前，先在草稿中记录事实和证据：

| 声明 | 证据类型 | 可信度 | 还缺什么 |
| --- | --- | --- | --- |
| 一次运行由后端准备证据，再交给 Pi | 调用链、测试 | 已确认 | 生产配置差异 |
| 取消会终止 Node 子进程 | 实现、单元测试 | 已确认 | 长工具调用时的时延 |
| 进程重启后可恢复某状态 | 仅从 UI 观察 | 未确认 | 持久化记录和重启实验 |

证据优先级通常是：

1. 已执行的测试或可复现实验。
2. 明确的协议、schema 和状态持久化。
3. 完整调用链中的实现。
4. 配置和部署定义。
5. 日志和运行时诊断。
6. 注释、旧文档和提交说明。
7. UI 表现或作者猜测。

如果运行时行为无法仅从代码确认，应在状态变化边界添加聚焦诊断，回答一个具体问题，再下结论。不要从 UI 症状反推内部原因，也不要把“可能是”润色成设计动机。

### 第三步：提取稳定模型

从证据中找出以下内容：

- 核心名词及其身份。
- 输入、输出和责任边界。
- 状态机和生命周期。
- 不能被破坏的不变量。
- 外部约束和失败模型。
- 可替代方案及真实代价。

然后尝试用一条不包含文件名和类名的流程表达系统。如果做不到，说明作者还停留在实现观察阶段，尚未形成文档模型。

### 第四步：按因果链组织正文

每个重要机制都可以用下面的顺序检查：

```text
问题是什么？
  -> 有哪些现实约束？
  -> 当前选择是什么？
  -> 它实际怎样工作？
  -> 哪些条件必须成立？
  -> 它付出了什么代价？
  -> 失败时怎样观察和恢复？
```

正文不必机械使用七个标题，但不能长期只停留在“它是什么”。连续五段都是“X 负责 Y”通常意味着因果密度不足。

### 第五步：用一条正常路径和一条异常路径验证

正常路径证明读者理解了主流程，异常路径证明边界和不变量不是装饰。例如：

- 正常：用户提问，范围被冻结，证据被准备，Pi 生成回答，结果和引用被保存。
- 异常：Pi 输出错误或进程被取消，哪些事件仍可见，哪些部分会持久化，用户是否可以重试。

如果文档无法说明异常路径，往往意味着作者尚未理解真正的所有权边界。

## 八、把低价值写法改成可推理的写法

### 例一：从文件定位改成运行边界

低价值写法：

> Pi Runtime 位于某个 Python 文件，Node runner 位于另一个文件，runtime factory 在第三个文件创建它。

更好的写法：

> Vidraft 把通用 Agent 循环交给 Pi，但继续拥有产品上下文、证据范围、运行记录和前端事件协议。Python 后端先把一次运行准备成稳定请求，Node 进程只负责执行 Pi session 并回传事件。这样可以复用 Pi 的编排能力，又不会让通用 runtime 反向拥有 Vidraft 的资源和引用语义。代价是两端必须维护一个明确、可测试的进程协议。

代码位置可以放在文末“实现证据”中，供准备修改的开发者验证；它不应打断架构主线。

### 例二：从入口函数改成召回语义

低价值写法：

> 自动召回入口是 `_with_recalled_citations`，它调用 retrieval store 并转换结果。

更好的写法：

> 每次召回先确定本轮允许使用的资源范围，再在范围内寻找候选材料，最后把内部命中转换为用户可核验的 Citation。范围必须早于检索确定，否则同一句问题可能因为入口不同而混入不应出现的资料。内部 Retrieval Hit 与对外 Citation 分离，是为了让检索实现可以替换，而对话和历史记录仍保留稳定的出处语义。

第二段让读者能够判断新检索能力应接在哪里，也能理解为什么不能让前端自行拼接来源。

### 例三：从参数罗列改成策略与参考分层

低价值写法：

> 章节召回最多 4 条，字幕召回最多 8 条，最终结果最多 8 条，模型输入最多 12 条。

更好的解释层：

> 视频召回先用章节级材料定位主题区域，再在命中区域寻找带时间信息的细粒度证据。粗到细的两阶段设计同时服务语义相关性和可核验定位；最终合并还要限制单一来源占比，避免一篇长文档挤掉其他证据。

易变的数量、阈值和默认值应进入紧邻的“当前参数”参考表，或者直接由配置 schema 生成。这样调整默认值不会让整篇架构解释失效。

### 例四：从 UI 组件清单改成用户可观察事实

低价值写法：

> 对话页包含消息列表、运行步骤组件、Citation 组件和停止按钮。

更好的写法：

> 对话界面需要区分三类事实：用户与 Agent 已经说了什么、当前运行正在发生什么、最终回答由什么证据支持。运行步骤可以是暂态信息，但最终回答、错误和 Citation 必须能够在刷新后恢复。停止操作改变的是运行生命周期，不应伪装成一条普通消息。

这种描述能指导任何前端实现，而不会与某个组件拆分绑定。

## 九、图应该帮助推理，而不是装饰页面

项目文档最有价值的图通常只有三种：

1. 关系图：回答稳定对象之间是什么关系。
2. 顺序图：回答一次请求或事件怎样跨越边界。
3. 状态图：回答对象能处于什么状态，什么触发迁移。

一张图应只回答一个问题。总览图尽量控制在 5 到 9 个节点，使用领域概念和责任名称，不使用几十个类名。复杂系统可以像 GitLab 一样提供“简化图”和“详细图”，但两张图必须明确服务不同读者深度。

图后必须有一段文字带读者走一遍主路径。图中每条重要箭头至少应能回答：

- 传递的是什么。
- 谁发起，谁拥有结果。
- 是同步、异步还是持久化边界。
- 失败会停在哪里。

以下图通常价值较低：

- 把目录树换成方框。
- 每个类一个节点但没有关系语义。
- 只有正常路径，没有状态和失败点。
- 图与正文使用不同名词。
- 自动生成后无人能够解释的全量依赖图。

## 十、四类文档的实用模板

模板用于防止遗漏，不应成为每篇文章都必须填满的表格。

### 架构或设计解释

```markdown
# 标题：用读者的问题命名

这篇文档帮助谁回答什么问题；不覆盖什么。

## 一句话模型

用一句话说明系统怎样把输入变成结果。

## 核心概念

只定义理解后文必需的稳定名词和关系。

## 端到端流程

一张小图，加一遍主路径说明。

## 关键边界与不变量

谁拥有数据、状态和失败；哪些条件必须始终成立。

## 为什么这样设计

问题、约束、当前选择、主要备选和代价。

## 失败与恢复

如何观察、重试、回滚或降级。

## 修改系统时的判断规则

新能力应接入哪里，哪些边界不能绕过。

## 当前限制

稳定限制与尚未完成的能力，不复制临时 bug 列表。
```

### 任务型操作指南

```markdown
# 完成某项任务

## 何时使用
## 前提和预期结果
## 操作步骤
## 每一步的可观察检查点
## 常见失败：症状、原因、解决办法
## 重试、回滚或清理
```

步骤不应只有命令。至少在关键步骤后写出预期状态，让读者知道是继续还是停止排查。

### 参考文档

```markdown
# 某项契约参考

## 适用范围和版本
## 精确字段、事件或配置
## 默认值和限制
## 最小有效示例
## 兼容性与弃用规则
## 权威来源或生成方式
```

能从 OpenAPI、类型、配置 schema 或命令帮助生成的内容，优先生成，不手工复制。

### 架构决策记录

```markdown
# 决策标题

状态：提议 / 已接受 / 已替代

## 背景和决策压力
## 必须满足的约束
## 考虑过的方案
## 决定及理由
## 正面和负面后果
## 何时需要重新评估
```

如果一项决定没有真实备选、长期后果和重审价值，就放入一份简短决策日志，不要单独建立 ADR。

## 十一、让文档不那么快过期

### 分离稳定知识与易变事实

稳定知识包括：

- 领域概念和身份。
- 数据所有权和边界。
- 状态机和不变量。
- 外部约束和重要取舍。
- 失败模型与恢复原则。

易变事实包括：

- 默认数量和阈值。
- 完整 API、字段和事件列表。
- 文件位置和类名。
- 当前模型名、依赖版本和命令参数。
- 临时 bug 和迁移进度。

稳定内容留在解释文档，易变内容进入生成参考、配置 schema、版本化说明或 issue tracker。两者混在一起，是长篇文档快速失真的主要原因。

### 每个事实只保留一个权威来源

文档可以解释一个事实的意义，但不应在多处复制同一份字段表或默认值。其他页面通过链接复用。尤其要避免：

- 架构页、部署页和 README 各写一套环境变量。
- 前端文档和 API 文档分别维护事件名称。
- 已知限制页面复制活跃 bug 列表。
- 多篇 topic 分别描述同一运行生命周期的不同片段。

### 用变更触发维护，而不是依赖定期善意

下列变更应触发对应文档检查：

- 新增或改变领域对象、状态和持久化语义。
- 跨越 Python、Pi、前端或存储边界。
- 修改公开 API、事件协议、配置和默认行为。
- 改变失败、重试、取消、备份或恢复行为。
- 替换一个被文档明确解释过的设计选择。

代码评审问题可以很简单：

> 这项改动是否改变了读者用来预测系统行为的模型？如果改变了，哪一篇权威文档必须一起更新？

### 删除也是维护

过期文档比缺少文档更危险，因为它会以权威语气提供错误模型。发现以下情况时应合并或删除：

- 页面只剩源码位置和类名。
- 内容已经由自动生成参考完整覆盖。
- 页面与另一篇文档回答相同问题。
- 功能已删除，页面只留下历史说明。
- 没有明确读者，也没有独立入口价值。

真正有长期价值的历史选择保留在决策记录中，而不是让旧操作说明继续出现在当前文档导航里。

## 十二、项目文档质量评估标准

可以对每个维度评分 0、1、2 分：0 表示缺失或错误，1 表示部分满足，2 表示读者可以依赖它完成推理或任务。

| 维度 | 评估问题 |
| --- | --- |
| 读者与目标 | 是否明确谁在什么情境下阅读，读完能做什么？ |
| 准确性与证据 | 关键声明能否由代码、测试、配置或运行证据支持？不确定性是否显式？ |
| 心智模型 | 是否用少量稳定概念解释系统，而非直接倾倒实现名词？ |
| How/Why | 是否同时解释流程、约束、选择、代价和主要备选？ |
| 边界与不变量 | 是否说明所有权、不能绕过的条件和安全边界？ |
| 失败与恢复 | 是否覆盖可观察症状、失败位置、重试、回滚或降级？ |
| 示例与可验证性 | 示例是否证明模型，并包含预期结果或检查方法？ |
| 信息架构与维护性 | 页面粒度是否合理，稳定和易变内容是否分离，是否有权威来源？ |

建议解释：

- 14 到 16 分：可以作为团队的权威文档。
- 11 到 13 分：可用，但存在明显推理缺口。
- 8 到 10 分：主要是事实摘要，需要重构。
- 低于 8 分：更像代码索引或自动生成草稿，不应作为权威入口。

准确性与证据如果是 0 分，无论总分多少都不应发布。一个写得流畅但动机虚构的页面，比一份明确承认未知的草稿更危险。

### 用任务而不是阅读感受验收

选择一位没有参与实现的开发者，让他只依赖文档完成以下测试：

1. 用五分钟画出系统主流程和主要所有权边界。
2. 解释为什么某项能力属于 Vidraft，而不是属于 Pi。
3. 预测一次资源重命名、运行取消或进程重启会影响哪些状态。
4. 给出一个新资料来源应接入的阶段，并说明理由。
5. 根据一个失败症状找到应该观察的状态边界。

如果读者必须重新通读目录和调用链才能回答，文档还没有完成知识传递。

## 十三、常见反模式

| 反模式 | 症状 | 为什么有害 | 修正方式 |
| --- | --- | --- | --- |
| 文件导游 | 每段以“某文件负责……”开始 | 路径易变，读者得不到系统模型 | 先写职责、流和所有权，路径降为实现证据 |
| 类和函数词典 | 大量并列定义，没有关系和时序 | 无法预测真实行为 | 选一条请求或数据流串起对象 |
| 一符号一 topic | 每个模块、工具、Prompt 都单独成页 | 上下文被重复，导航成本转嫁给读者 | 按读者问题合并为主文档章节 |
| 虚构 Why | 使用“可扩展、灵活、解耦”等空泛理由 | 掩盖未知，后续决策无法复用 | 写出具体约束和证据；不知道就承认 |
| 只有正常路径 | 文档在“返回结果”处结束 | 真正所有权往往只在失败时显现 | 增加超时、取消、部分写入、重启和恢复 |
| 易变数字污染架构 | 阈值和默认值散落全文 | 参数一改，整个模型看似过期 | 解释策略，数字集中到参考区 |
| 图即架构 | 一张全量组件图代替正文 | 图无法表达理由、不变量和代价 | 一图一问，并用文字走通主路径 |
| 多份事实副本 | 多页重复字段、配置或状态表 | 内容必然漂移 | 建立单一权威来源，其他页面链接 |
| ADR 仪式化 | 三五行也单建 ADR | 决策记录失去检索价值 | 小决定进决策日志，重大选择才建 ADR |
| AI 一次性生成全库 | 页面很多、句子流畅、缺少因果 | AI 优先复述可见结构并填补动机 | 分离证据提取、模型综合和人工验证 |

## 十四、让 AI 写出更好的项目文档

问题通常不在 AI 不会写句子，而在任务被描述成“扫描仓库并生成文档”。这种任务天然鼓励它把目录、类、路由和配置重新排列一遍。高质量流程应分三轮。

### 第一轮：只收集证据，不写成文

要求 AI 输出：

- 核心对象及其关系。
- 一条完整调用或数据流。
- 状态变化和持久化边界。
- 测试证明了什么。
- 已确认的约束和失败行为。
- 无法由静态代码确认的问题。

禁止它在这一轮补充历史动机。

### 第二轮：综合成因果模型

让 AI 对每个重要机制回答：问题、约束、选择、机制、不变量、代价、失败和恢复。要求它区分：

- 代码直接证明的事实。
- 从多个证据合理归纳的结论。
- 需要作者确认的未知。

只有这一轮完成后，才决定页面边界。

### 第三轮：按读者任务写作和删减

可以直接使用下面的提示词：

```text
你正在为需要安全修改和排障该系统的开发者编写项目文档。

先声明本文服务的读者问题和不覆盖的范围。不要按目录、文件、类或函数组织正文。
先用少量稳定概念建立心智模型，再沿一条真实请求、数据或状态流解释系统。

对每个关键机制，说明：
1. 它解决什么问题；
2. 有哪些现实约束；
3. 当前为什么采用这个选择；
4. 实际怎样运行；
5. 哪些不变量必须成立；
6. 主要代价或被放弃的方案；
7. 失败时如何观察、恢复或重试。

只写有证据支持的 Why。无法从代码、测试、配置或运行证据确认的动机必须标记为未知，
不要用“为了扩展性、灵活性、解耦”填空。

代码路径和符号只作为文末的实现证据，不作为叙述主线。易变默认值放入参考区，不混进稳定架构说明。
至少给出一条正常路径和一条异常路径，并说明读者如何验证预期结果。

新建页面前先判断它是否有独立读者、独立任务或独立维护周期；否则把它作为现有主文档的章节。
完成初稿后，删除重复背景、显而易见的代码复述、无因果作用的清单和无法证实的理由。
```

### AI 适合做什么，不适合替代什么

AI 很适合：

- 追踪跨文件流程并形成证据账本。
- 找出术语不一致和重复内容。
- 把同一事实的多处描述合并。
- 根据已确认模型生成图、示例和初稿。
- 用质量量表检查缺失章节。

AI 不应独自决定：

- 没有记录的历史动机。
- 产品边界和未来承诺。
- 运行时无法静态确认的行为。
- 哪个权衡对团队最重要。
- 一项旧设计是否仍是当前意图。

这些地方需要作者确认、运行实验或明确决策。

## 十五、Vidraft 文档重构的建议顺序

不建议逐篇润色现有 62 个 topic。更有效的顺序是：

1. 先确认 Vidraft 当前稳定的领域词汇和产品循环。
2. 写出一篇系统架构和三条主流程：资源进入、证据召回、Agent 运行。
3. 单独确认 Pi 迁移后的责任边界，移除旧 runtime 模型留下的叙述。
4. 按本文建议的 10 到 11 个读者问题建立主文档。
5. 将现有 Almanac 页面映射到这些主文档，只迁移有证据的 Why、不变量、失败经验和决策。
6. 把字段表、API、配置和事件协议迁到生成参考或集中参考章节。
7. 删除被合并的 topic，而不是保留两套入口。
8. 用真实修改任务和排障任务验收，再把主文档设为权威导航。

迁移过程中最重要的不是“旧内容一个字也不能丢”，而是区分四类内容：

- 必须保留的稳定设计知识。
- 应集中管理的易变参考。
- 可由代码重新获得的低价值复述。
- 已过期或无法证实的叙述。

只有前两类需要进入新的 `docs/`。

## 十六、最终检查清单

发布一篇项目文档前，逐项确认：

- [ ] 标题对应读者问题，而不是代码模块名。
- [ ] 开头说明读者、目标和范围。
- [ ] 前几段给出一句话模型或主流程。
- [ ] 核心术语少量、稳定且全文一致。
- [ ] 正文主要围绕流、状态、边界和决定展开。
- [ ] 每个重要 Why 都有具体约束或证据。
- [ ] 没有替历史作者补造动机。
- [ ] 写清所有权和至少一个关键不变量。
- [ ] 同时覆盖正常路径和异常路径。
- [ ] 重要替代方案和负面后果没有被省略。
- [ ] 示例能验证模型，并写出预期结果。
- [ ] 文件路径没有成为正文骨架。
- [ ] 易变参数与稳定解释已经分离。
- [ ] 没有与其他页面维护同一份事实副本。
- [ ] 新页面确实有独立读者任务或维护周期。
- [ ] 读者可以只靠本文做出至少一个真实修改或排障判断。
