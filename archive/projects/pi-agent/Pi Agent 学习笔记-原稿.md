# Pi Agent 学习笔记

这篇记录 Pi Agent 的架构、工具调用和上下文管理机制，重点理解一个 Agent 如何在有限上下文中持续、安全地执行长任务。

## 学习资料

- [How Pi Agent Works：Pi Architecture](https://how-pi-agent-works.vercel.app/concepts/pi-architecture)

## 核心架构认识

Pi Agent 将消息分成三类基础消息：`user`、`assistant` 和 `tool`。

```ts
type Message = UserMessage | AssistantMessage | ToolResultMessage;
```

Pi Agent 的核心思想，是固定 Agent 运行所必需的稳定知识，并隔离不稳定的外部环境。流式事件负责提供实时反馈。

## 工具调用

一个工具主要包含以下信息：

- `description`：说明工具用途，影响模型何时调用它。
- `name`：稳定的工具名称。
- 参数 schema：定义运行参数并负责校验。
- 执行函数：真正完成工具行为。
- before hook 与 after hook：在执行前后提供拦截和扩展点。

### 并行与串行

Pi 支持同一条助手消息里包含多个工具调用。默认可以并行，但某些具有副作用或前后依赖的工具需要串行。

| 模式 | 适合场景 | 风险或代价 |
| --- | --- | --- |
| `parallel` | 多个只读操作，例如 `grep`、`read`、`find` | 输出完成顺序可能不同，回写时仍需保持原始调用顺序 |
| `sequential` | 写文件、执行依赖前一步结果的命令 | 速度较慢，但更容易保证副作用顺序 |

Pi 的做法是：并发执行允许并发的工具，但生成 `toolResult` 消息时仍按助手原始的 tool call 顺序写回，避免模型看到错乱的上下文。

这段内容真正讲的，不只是“Pi 会把旧消息压缩成摘要”，而是：

> **Pi 在解决一个长期运行 Agent 必然遇到的问题：模型的上下文有限，但任务可能持续很久，甚至跨越多次工具调用、多个会话分支。**

## 上下文压缩：为什么需要它

Agent 的历史会不断增长：

```text
用户消息
→ 模型回复
→ 工具调用
→ 工具结果
→ 再次回复
→ 更多工具调用
```

如果每次都把全部历史发给模型，迟早会超过 Context Window。

直接删除旧消息又不行，因为 Agent 会忘记：

* 用户最终想完成什么；
* 已经修改了哪些文件；
* 为什么做出某个设计决定；
* 当前卡在哪里；
* 接下来应该做什么。

所以压缩的目的并不是“减少聊天记录”，而是：

> **把庞大的原始历史转换成一份较小但仍能继续工作的工作记忆。**

## 当前上下文最终长什么样

正常情况下，LLM 看到的不是很多份摘要，而是：

```text
System Prompt
+
最新的一份累计 Summary
+
最近保留的原始消息
```

Session 日志中可能保存着 `summary1`、`summary2`、`summary3` 等多个压缩条目，但它们属于历史记录。

真正发送给模型时，通常只使用当前有效的最新摘要。

所以需要区分：

```text
Session = 完整历史和事件日志
Prompt = 本次实际发送给模型的有限上下文
```

Session 可以越来越大，Prompt 必须始终受控。

## 摘要是如何逐步更新的

历史太长时，不可能每次重新把全部原始消息发给模型。例如原始历史已经有 500k token，而模型上下文只有 128k，完整重算根本做不到。

因此它采用的是增量更新：

```text
summary1 = summarize(chunk1)

summary2 = update(summary1 + chunk2)

summary3 = update(summary2 + chunk3)
```

也就是：

```text
旧摘要
+
这次新进入压缩区的消息
↓
新的完整摘要
```

新的摘要不是只记录新增内容，而是要**替代旧摘要**，继续保留过去仍然重要的信息。

为什么这样设计？因为它允许 Agent 的会话在理论上持续很久，而每次压缩请求仍然保持在模型上下文限制之内。

代价是摘要可能发生信息漂移，所以摘要 Prompt 必须明确要求保留：

* 目标；
* 约束；
* 进度；
* 关键决定和理由；
* 阻碍；
* 下一步；
* 关键文件与数据。

## `firstKeptEntryId` 为什么存在

`firstKeptEntryId` 表示：

> **从哪一条消息开始，后面的原始消息仍然直接保留在上下文中。**

例如：

```text
旧历史 1–100 → 已经写进 Summary
最近消息 101–120 → 原样保留
```

那么 `firstKeptEntryId` 就指向 101。

它解决两个问题：

第一，Prompt Builder 知道应该拼成：

```text
Summary + 消息 101–120
```

而不是重新加入 1–100。

第二，下次压缩时，系统知道哪些最近消息尚未被吸收到累计摘要里。

所以它不是“重新读取全部原始历史”的索引，而是**摘要区和原始保留区之间的边界**。

## 为什么通常按 Turn 切割

一个 Turn 从一条用户消息开始，到下一条用户消息之前结束，里面可能包含：

```text
User
Assistant
ToolCall
ToolResult
Assistant
ToolCall
ToolResult
```

Pi 通常尽量在完整 Turn 的边界上切割。

为什么？因为一个 Turn 往往代表一段完整的任务过程。如果从中间切开，可能导致：

* 工具调用被保留，工具结果却被摘要；
* 工具结果被保留，却看不到对应调用；
* 模型只看到半截因果链；
* 当前任务的上下文变得难以理解。

因此，完整回合是最自然的压缩单元。

## 为什么还需要 Split Turn

有时单个 Turn 本身就特别大，例如用户让 Agent：

```text
分析整个仓库并运行大量工具
```

这一轮可能已经超过 `keepRecentTokens`。

这时没办法完整保留整个 Turn，只能从回合中间切开：

```text
回合前半段 → 摘要
回合后半段 → 原始保留
```

这就是 Split Turn。

此时 Pi 会区分：

```text
messagesToSummarize
```

用于表示之前的完整回合；

以及：

```text
turnPrefixMessages
```

用于表示当前超大回合被切掉的前半部分。

如果没有之前的完整回合，可能出现：

```text
messagesToSummarize = []
turnPrefixMessages = [当前回合前半段]
```

为什么要单独处理？因为“过去已经结束的任务历史”和“当前仍在进行的超大回合前半段”语义不同。

前者是背景，后者是当前工作的直接前因，摘要时不能简单混为一谈。

## 为什么不能在 ToolResult 处随便切

工具调用和工具结果必须保持对应关系：

```text
Assistant ToolCall
↓
ToolResult
```

如果只保留 ToolResult，模型不知道：

* 哪个工具被调用了；
* 参数是什么；
* 结果对应哪个 `toolCallId`。

如果只保留 ToolCall，没有结果，模型又可能误以为工具仍未执行。

所以有效切点可以放在用户消息、助手消息或某些独立自定义消息之前，但不能随意让工具结果脱离它对应的工具调用。

这不是格式洁癖，而是为了维持消息历史的**因果完整性**。

## 为什么摘要要结构化

Pi 的 Summary 不是普通的散文总结，而是类似：

```text
Goal
Constraints & Preferences
Progress
Key Decisions
Next Steps
Critical Context
read-files
modified-files
```

原因是 Agent 需要的不是“对话大意”，而是“继续工作的最小充分状态”。

普通总结可能写：

> 用户和助手讨论了登录模块，并修改了一些代码。

这种话几乎不能帮助下一个模型继续工作。

结构化摘要则会告诉它：

```text
目标是什么
已经完成什么
为什么选择当前方案
修改了哪些具体文件
还有什么错误
下一步执行什么
```

因此 Summary 本质上更像：

> **Agent 的任务检查点。**

而不是聊天内容的缩写。

## 为什么记录读过和改过的文件

编码 Agent 最重要的长期状态之一，是它已经接触过哪些代码。

因此摘要会累计记录：

```text
readFiles
modifiedFiles
```

这样多次压缩之后，Agent 仍然知道：

* 哪些文件已经检查过；
* 哪些文件被修改过；
* 后续需要重点复查哪些位置。

否则每次上下文压缩后，Agent 可能重复扫描整个项目，浪费 token 和工具调用。

## 压缩 Prompt 真正需要完成什么

这份文档展示了摘要格式、输入序列化方式以及可传入的字段，但没有完整贴出默认 Prompt 的逐字源码。

不过从设计上看，Prompt 的核心要求应该是：

```text
根据旧摘要和新增历史，生成一份新的完整工作摘要。

新摘要必须能够替代旧摘要，让另一个 Agent 在看不到原始历史时仍能继续任务。
```

重点不是“总结这段对话”，而是：

```text
保留继续工作所需要的一切
舍弃不能影响后续行动的细节
```

这就是为什么好的压缩 Prompt 必须强调 Why、决策原因和未完成事项，而不能只记录“发生过什么”。

## 整体设计思想

可以把 Pi 的压缩机制理解成三层：

```text
原始 Session
保存完整事实、分支和历史压缩条目

↓

Compaction
把过旧的工作历史转成结构化工作记忆

↓

当前 Prompt
System + 最新 Summary + 最近原始消息
```

它真正解决的是：

> **如何让一个受限上下文窗口的模型，表现得像拥有较长期、可持续更新的工作记忆。**

所以压缩并不是简单地节省 token，而是在三个目标之间做平衡：

```text
不能让上下文溢出
不能让 Agent 丢失任务状态
不能破坏工具调用和消息之间的因果关系
```

这也是为什么它需要累计摘要、保留边界、Turn 切割、Split Turn、结构化格式和文件追踪这一整套机制。


## 为什么保留最近消息

因为 **压缩的目标不是“随便砍掉一半”**，而是：

> **尽量保留离当前时刻最近、最可能马上继续用到的内容。**

所以在一个超大回合里，通常会把**较早发生的前半段**压缩掉，把**较新的后半段**原样保留。

可以把一个超长回合看成这样：

```text
用户提出任务
↓
助手开始分析
↓
调用工具 A
↓
得到结果 A
↓
继续分析
↓
调用工具 B
↓
得到结果 B
↓
助手正在基于最新结果继续处理
```

如果必须切一刀，更合理的是：

```text
较早部分 → 摘要
较新部分 → 原样保留
```

因为后半段通常包含：

* 最新工具结果
* 当前正在处理的状态
* 最近做出的判断
* 下一步最直接的上下文
* 尚未完成的动作链

这些内容对模型接下来继续工作最重要。

反过来，如果压缩后半段、保留前半段，就会变成：

```text
保留：
用户最初说了什么
助手一开始怎么想

压缩：
刚刚拿到的工具结果
当前做到哪里
下一步准备干什么
```

这会很别扭。模型能看到任务开头，却看不到最新进展，像是保留了会议开场白，却把最后五分钟的决策纪要压成一句话。

还有一个原因是 **时间局部性**。程序和 Agent 都常利用这个原则：

> 越近发生的信息，越可能马上再次被使用。

比如 Agent 刚读完 `package.json`，下一步很可能就要根据里面的内容修改配置。此时工具结果最好保持原文，而不是先压成摘要。

所以 `keepRecentTokens` 的含义本身就是：

```text
保留最近的若干 token
```

系统会从后往前数，尽量留下最新内容；超出预算的较旧部分才进入摘要。

不过这里的“前半段”不是机械地按 50% 切。它实际会寻找一个**合法切点**，例如某条 Assistant 消息之前，并保证不会把 `toolCall` 和对应的 `toolResult` 拆得失去语义。

可以记成一句话：

> **摘要负责保存“我们是怎么走到这里的”，原始近期消息负责保存“我们现在具体正在做什么”。**

## 结构化总结：任务检查点

这个“结构化总结”本质上不是普通的聊天摘要，而是一份给 Agent 续工作的**任务检查点**。

它通常这样生成：

```text
旧 summary
+ 本次需要压缩的新消息
+ 分裂回合前缀（如有）
+ 文件操作记录
↓
LLM 按固定模板生成新的完整 summary
```

模板大致包括：

* `Goal`：用户最终想完成什么
* `Constraints & Preferences`：有哪些限制和偏好
* `Progress`

  * `Done`：已完成
  * `In Progress`：正在进行
  * `Blocked`：被什么卡住
* `Key Decisions`：做了哪些关键决定，以及为什么
* `Next Steps`：接下来应该做什么
* `Critical Context`：继续任务必须知道的信息
* `read-files / modified-files`：读过、改过哪些文件

它为什么要结构化？因为普通总结很容易只写成“讨论了什么”，但 Agent 真正需要的是：

> 目标是什么、做到哪了、为什么这么做、卡在哪里、下一步做什么。

实现上，LLM 负责提炼语义；程序负责控制输入、规定格式、截断过大的工具结果，并单独累计文件记录。最后，这份内容会保存进 `CompactionEntry.summary`，替代旧摘要，和最近的原始消息一起组成下一轮上下文。

一句话概括：

> **结构化总结就是把漫长对话压缩成一份可恢复、可继续执行的 Agent 工作状态。**

## Branch Summary：跨分支交接

**Branch Summary（分支总结）**就是：

> 当你从当前对话分支跳到另一条分支时，把“你即将离开的这条路线做过什么”压缩成一份摘要，带到新分支里。

举个例子：

```text
A：帮我设计登录系统
├─ B：走 JWT 方案
│  ├─ C：实现 token 刷新
│  └─ D：修复过期问题   ← 你现在在这里
└─ E：改走 Session 方案 ← 你准备跳到这里
```

从 `D` 跳到 `E` 时，Pi 会先找它们的共同祖先：

```text
共同祖先：A
```

然后把旧分支里独有的部分：

```text
B → C → D
```

总结成类似：

```md
## Goal
实现登录系统

## Progress
- 已完成 JWT 登录
- 已实现 refresh token
- 修复了 token 过期处理

## Key Decisions
- 使用双 token 机制
- refresh token 存入 HttpOnly Cookie

## Modified Files
- src/auth.ts
- src/token.ts
```

然后把这份摘要注入到你切换后的分支上下文中。

### 为什么需要它

因为你跳到新分支后，模型默认只能看到新分支上的历史。

如果不做 Branch Summary，旧分支里发生的这些事就“消失”了：

* 改过哪些文件
* 试过什么方案
* 哪些方案失败了
* 做了哪些关键决定

Branch Summary 的目的就是：

> **让新分支继承旧分支的工作成果，但不把整条旧分支的所有原始消息都塞进上下文。**

### 它和 Compaction Summary 的区别

| 类型                 | 解决的问题            |
| ------------------ | ---------------- |
| Compaction Summary | 当前分支太长，压缩旧历史     |
| Branch Summary     | 切换分支时，把被离开的路线带过去 |

可以这样记：

```text
Compaction：沿时间轴压缩
Branch Summary：跨分支搬运上下文
```

一句话总结：

> **Branch Summary 是“离开一条对话路线时留下的交接说明”。**
