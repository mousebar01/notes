# 视频智能体论文工程落地复盘

> 来源：一次论文项目复现后的个人判断；当前笔记没有附运行日志、测试素材或上游 commit。
>
> 采用状态：作为项目范围收缩的主要依据。暂定主线仍待作者最终确认。
>
> 结论：先验证 `storyboard -> retrieval -> trim -> 拼接`，不把通用多 Agent 视频生产当作近期目标。

大概率不是实现能力的问题，而是这个项目本身的**论文叙事和工程可执行性之间断层太大**。

你做了一天越做越不对，通常会卡在这几个点：

1. **论文把“规划一个流程”包装成了“完成视频编辑”**
   但实际一跑就会发现，LLM 生成 agent graph 很容易，真正难的是每个节点都要有稳定输入输出、错误恢复、格式对齐、时间轴统一。

2. **很多 agent 名字像功能，实际上不是可用模块**
   比如 Writer、RhythmDetector、VideoEditor、VoiceCloner、LipSync、SubtitleEditor 这些，论文里可以当节点画出来；工程里每个都是一个独立项目，接口、依赖、质量都不稳定。

3. **视频剪辑不是纯 pipeline，更多是反复试错**
   自动剪辑需要不断看结果、调整节奏、换镜头、修音画同步。论文的 graph optimization 只优化“流程结构”，没有真正解决“成片质量反馈”。

4. **它的 benchmark 可能验证的是 orchestration，不是 end-to-end production**
   也就是判断“这个流程图是否合理”，而不是“最终视频是否真的好”。所以你复现时会觉得：指标看起来挺高，但做起来完全不是一回事。

所以你现在最应该做的不是继续硬复现全套，而是**收缩目标**。
我建议你把它拆成三个层级：

**能做的：**
自然语言需求 → 生成 storyboard → 从素材库检索片段 → 简单 trim → 拼接成视频。

**勉强能做的：**
加 BGM、节拍点检测、字幕、旁白、基础转场。

**先别碰的：**
通用 multi-agent graph optimization、任意视频编辑 agent、自动换脸、lip-sync、多情绪 voice cloning、meme/crosstalk/song remix 这种复杂创作链。

如果你是为了复现论文，可以写得很明确：**“本文优先复现 shot planning + retrieval + trimming 子系统；完整多 agent 编辑流由于 agent library 缺少可执行实现、I/O schema 不明确、端到端质量评估缺失，暂不作为复现重点。”**

这不是退缩，反而是更靠谱的判断。你现在的直觉基本是对的：**别再按论文的 all-in-one 叙事往下硬做，先把它降级成一个可运行的 retrieval-based video montage system。**


基本上很难有类似的直接能实现的项目，所以不要被论文所宣称的故事欺骗。
