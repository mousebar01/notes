# Yuxi 多智能体与后台任务

这篇记录 Yuxi 如何在聊天 Agent 上增加子智能体委派能力，以及它为什么没有把所有自动化任务都建模成子 Agent。

> 观察版本：[xerrors/Yuxi@a8a933d](https://github.com/xerrors/Yuxi/tree/a8a933d3dcfd27d310d43c36054fe103cec3e85b)。本文是源码学习笔记，不是官方设计说明。

## 核心结论

Yuxi 采用的是“主 Agent 聊天，子 Agent 工具化”的模式：

```text
用户
  -> ChatbotAgent
      -> 普通工具 / 知识库 / Skill / MCP
      -> task(description, subagent_type, thread_id?)
          -> SubAgentBackend
          -> child graph / child thread
      -> 主 Agent 汇总结果
```

子 Agent 是语言型、研究型和审查型任务的委派单元。知识图谱提取等确定性后台处理仍由 service、worker 或任务系统负责。

## 主 Agent 如何获得委派能力

主 Agent 使用 LangChain `create_agent(...)` 创建 graph，并在 middleware 链中按当前配置挂载子智能体能力：

```python
graph = create_agent(
    model=load_chat_model(...),
    tools=await resolve_configured_runtime_tools(context),
    system_prompt=build_prompt_with_context(context),
    middleware=await _build_middlewares(context),
    state_schema=ChatBotState,
    checkpointer=await self._get_checkpointer(),
)
```

`_build_middlewares()` 只有在当前 Agent 存在可见子智能体时，才加入 `YuxiSubAgentMiddleware`。因此，数据库里存在某个子 Agent，不代表当前会话一定能调用它。

具体实现入口是 [`subagent_task.py`](https://github.com/xerrors/Yuxi/blob/a8a933d3dcfd27d310d43c36054fe103cec3e85b/backend/package/yuxi/agents/middlewares/subagent_task.py)。

## 配置与数据模型

子智能体仍然是 `agents` 表中的 Agent 配置，而不是另一套独立实体。它通过以下信息区分：

- `is_subagent=true`
- 专用 `SubAgentBackend`
- 主 Agent `subagents` 配置决定当前可调用范围

这个设计让子 Agent 可以复用普通 Agent 的模型、工具、知识库、MCP 和 Skill 配置，同时由 backend 与 middleware 限制其运行方式。

## `task` 工具

middleware 会向主 Agent 注入可用子智能体说明，并暴露一个 `task` 工具：

| 参数 | 含义 |
| --- | --- |
| `description` | 给子 Agent 的独立任务说明 |
| `subagent_type` | 要调用的子智能体 slug |
| `thread_id` | 可选；继续已有子任务线程 |

调用过程可以概括为：

1. 校验 `subagent_type` 是否在允许范围内。
2. 读取父线程、用户和文件线程信息。
3. 确认目标使用 `SubAgentBackend`。
4. 创建或复用 child thread。
5. 创建 `run_type="subagent"` 的运行记录并关联父 run。
6. 构造子智能体 context 和输入消息。
7. 执行子 graph。
8. 更新完成或失败状态。
9. 将最终文本和 child thread id 作为 `ToolMessage` 返回主 Agent。

## 状态、恢复与事件

主 Agent 和子 Agent 都运行在 LangGraph graph 上，并通过 checkpointer 保存 thread state。观察版本支持 Postgres、SQLite 和内存回退路径。

child thread 的价值不只是记录一次调用：

- 子任务有独立上下文，不必继承完整主对话。
- `thread_id` 可以继续同一个子任务。
- run 记录能表达 running、completed、failed 等状态。
- 流式事件带有父子线程、子 Agent 类型和 tool call 等路由信息，前端可以区分事件来源。

子 Agent 自身不再挂下一层 `task` middleware，避免无限嵌套。这个限制也意味着复杂层级编排应由主 Agent 或显式工作流承担。

## 内置角色

| 角色 | 职责 |
| --- | --- |
| `general-purpose` | 通用分析、整理、写作或文件处理 |
| `web-search` | 网页检索和带来源的信息整理 |
| `research-explorer` | 围绕单个子问题收集证据 |
| `fact-verifier` | 核查论断并给出支持、存疑或反驳 |

`deep-research` 是会调度 `research-explorer` 和 `fact-verifier` 的主 Agent，不是普通子 Agent。这个区别避免把“编排者”和“被委派角色”混成同一层。

## 子 Agent 与后台任务的边界

适合子 Agent：

- 需要语言理解或推理的独立子问题
- 检索、研究、核查、总结和草稿生成
- 希望隔离上下文并保留子任务线程的工作

不应仅因为任务在后台运行就使用子 Agent：

- 知识图谱批量抽取
- 文件解析、向量化和索引构建
- 定时清理、数据同步和状态维护
- 有确定输入输出与重试规则的长任务

后者更适合 service、worker 或持久任务系统。子 Agent 解决的是认知任务委派，后台任务系统解决的是可靠执行。

## 设计取舍

这套模式的优点是用户始终只面对一个主聊天对象，多 Agent 复杂性留在执行层；需要透明度时再展示子 run、工具事件和来源。

需要持续验证的边界包括：

- 子 Agent 是否应共享主会话文件和产物权限。
- 并行 `task` 调用的限流、取消和失败聚合策略。
- child thread 的保留时间与清理规则。
- 子 Agent 输出进入主上下文前是否需要长度限制和来源标记。

一句话总结：

> Yuxi 把子 Agent 设计成主 Agent 可调用的有状态专家工具，而没有把所有后台自动化都包装成 Agent。
